## 1. 产品目标与隔离边界

REQ-01：pCryoxy 是独立的新项目，与 pRayShell 的仓库、文档、任务、配置和运行数据隔离；不迁移、不覆盖、不修改旧项目的成果。【v1.3】项目代码仓已建立（PC-00 done，远端为 Gitee），主线 `main` 只接受审核通过后的合并。

REQ-02：产品是现代加密代理协议的图形化前端和调度外壳，用来解决多个节点不稳定、断流和速度波动的问题。通过策略组、健康探测、分流和自动选路提高可靠性；不重写代理协议内核，不承诺把多个节点的带宽叠加到一条连接上。

REQ-03：第一阶段（P0）正式支持 Windows、Android、Linux；macOS、iOS、鸿蒙 NEXT 列为第二阶段。Linux P0 同时覆盖无桌面的服务器/软路由环境和桌面环境；无桌面路径不得依赖 WebKitGTK；代理接管支持本地 SOCKS/HTTP 入站和 Xray 原生 tun 模式。系统路由、权限和发行版差异在蓝图和验收卡中明确，不能把预留能力当成已经实现。【v1.3】原 REQ-25 已并入本条。鸿蒙 NEXT 的技术路线（例如 VpnExtensionAbility、NAPI 桥接、ArkUI 壳）只作为参考记录，进入第二阶段时再定方案。

## 2. 技术路线与模块化

REQ-04：Rust＋Tokio 负责订阅解析、独立 IR、并发探测、健康状态、调度、核心控制、更新管理和 AI 工具总线；Tauri v2 作为壳，界面用 SolidJS＋TypeScript＋Tailwind CSS。Android 允许必要的原生桥接和平台服务，不要求所有平台代码都用 Rust。

REQ-05：采用 Rust Workspace，规划 core-ir、plugin-sdk、engine-scheduler、plugin-xray、core-updater、plugin-ai-agent、tauri-app 等职责边界。IR 不依赖任何一种核心的配置格式，由核心适配器生成配置。首期只做 Xray，后续为 sing-box、Mihomo 预留。模块化不要求首期就实现外部动态插件加载。

REQ-06：拟定 ProxyCorePlugin、ProtocolParserPlugin、RoutingStrategyPlugin、AiAssistantPlugin 等必要接口。start、stop、hot_reload、sync_outbounds、get_traffic_stats 是原始的接口意图，最终签名和能力限制由蓝图确定；不能用统一接口掩盖「各平台并非都能热更新所有配置」这一事实。

## 3. 功能与优先级

| 优先级 | 功能范围 |
|---|---|
| P0 | 节点连接、订阅与分享链接导入、订阅定时更新、去重、生命周期、健康探测、故障转移、最低延迟、按新连接轮询、基础分流、Geo 管理、核心更新与回退、平台生命周期、状态与流量展示；Windows/Linux 本地访问日志（REQ-33～36，见 §9） |
| P1 | AI 完整工具调用、吞吐测速的高级功能、一致性哈希负载均衡；【v1.3 拆分】① 本地入站的进程分流（Windows/Linux，基于固定核心的 `process` 条件，不需要 TUN）；② Windows TUN 接管（以及只有 TUN 才能覆盖的、不走系统代理的程序） |
| 后续 | 其他代理核心和其他平台，不阻塞第一阶段 |

REQ-07：解析订阅，以及 vless://、vmess://、trojan://、ss://、hy2:// 等标准分享链接。节点去重使用协议、地址、端口和核心凭证指纹；同一端点但传输或安全配置不同的节点如何判定身份，由蓝图明确（已由 G2 裁定：八字段指纹，语义冲突返回 `FingerprintConflict`），不能直接误合并。节点状态包括活跃、降级、失效隔离、自动恢复，并展示历史可用率、抖动和延迟。

REQ-08：保留以下能力需求：VLESS（Vision、VLESS Encryption）、VMess、Trojan、Shadowsocks（SS-2022）、Hysteria2、WireGuard、MASQUE，以及 RAW、XHTTP、WebSocket、HTTPUpgrade、gRPC、REALITY、TLS、FinalMask。代理协议、传输、安全和附加能力分别建模，按固定核心发行版、平台和配置组合建立支持矩阵。常用组合提供表单，其余已支持的能力提供高级入口；不支持的组合明确拒绝，不静默丢字段。
【v1.3 落实裁定】人类 11-22 00:11 裁定不接受 P0 缩减。PC-04b（11-23 结卡，main `c3acc73`）已在桥的受限 profile 中纳管 sniffing、freedom 直连、FinalMask 白名单类型和 localhost DNS。FinalMask 在 IR 里还表达不了，由 PC-07 走契约变更承接；FinalMask 没有完成三栏取证之前，PC-07 不得结卡。被明确拒绝的类型（realm、xicmp、udphop 等）在支持矩阵里列为「拒绝」，并写明原因。

## 4. 健康、调度与连续性

REQ-09：启用策略组后，自动执行轻量的真实 HTTP 204 代理链路探测；吞吐测速只能由用户主动触发。最低延迟容差默认 50ms；其余参数已由 G5 裁定：周期 30s、超时 5s、并发 16、连续失败 3 次隔离、连续成功 2 次恢复。

REQ-10：同一策略组同一时刻只允许一个选路决策方。首期由 Rust 负责健康、防抖和选路，Xray 执行动态路由。P0 包含故障转移、最低延迟、按新连接轮询；一致性哈希放在 P1。原生 burstObservatory／balancer 自动优选只能作为明确分开的模式，不与 Rust 同时控制同一个组；是否实现这个独立模式，不作为未经确认的新增 P0。

REQ-11：正常的节点切换和故障转移，不能把重启核心进程作为常规实现。故障时允许连接重建；核心升级允许有维护窗口；不承诺绝对零断流。轮询的「每连接选择」、存量连接保留和并发语义，必须通过实现分析和测试来验证，不能把全局覆盖目标说成严格的逐连接轮询。

REQ-12：所有代理组都失效时，应走代理的流量直接失败，不自动转直连；明确的直连规则继续生效。Windows 系统代理模式不承诺全系统防泄漏；Android VPN 内的失败策略和系统级阻断选项分开说明。
【v1.3 澄清：全失效时的 DNS 边界】
- P0 内置 DNS 只允许空列表或 `localhost`，也就是使用系统解析器，由桥的 `validateIsolatedDNS` 强制；远端 DNS 和 FakeDNS 在 P0 一律拒绝（远端 DNS 的策略转 P1/PC-12）。所以 DNS 本身不依赖代理节点，全失效时直连规则的域名解析和 GeoIP 匹配仍能工作。
- 边界：按 IP 类规则匹配时，可能用系统 DNS 解析目标域名，这部分查询不经过代理。这属于本条已声明的「系统代理模式不承诺全系统防泄漏」范围，不另外承诺 DNS 防泄漏。
- 验收：PC-09 和 PC-12 各增加一条：所有节点都不可用时，直连的域名规则以及 `geoip:private`、`geoip:cn` 直连规则仍能连通，应走代理的流量明确失败、不转直连。Android 在 PC-11 的 VPN 场景单独取证。

## 5. 平台接管、分流与 Geo

REQ-13：Windows P0 提供本地代理和系统代理，TUN 放到后续（【v1.3】PC-04b H1 已在 Windows 构建中拒绝 tun）。Android P0 使用系统 VPN 接管，支持按应用选择是否纳入 VPN；服务生命周期、系统授权、后台运行和防环路由在蓝图中落实。
【v1.3 澄清：Android 按应用分流】
- 两种模式，二选一：「仅所选应用走 VPN」（白名单）和「所选应用不走 VPN」（黑名单）。原因：系统接口 `addAllowedApplication` 和 `addDisallowedApplication` 不能在同一个 VPN 会话里混用。
- 需要读取已安装应用列表，以便用户选择。所需权限或 `<queries>` 声明由 PC-11 提出依据，按依赖/权限申请流程审批。
- 应用以包名（package name）标识，不以显示名称作为身份。所选应用卸载后，不能静默影响其他规则。
- 验收：PC-11 在真机上两种模式各验证一例，并确认未纳入的应用不经过 VPN；PC-15 提供应用选择界面。
- 本澄清只涉及 Android。Windows、鸿蒙的按应用/按进程字段，等对应卡建模时再定，不在现在预留空字段（见 REQ-14、§13）。

REQ-14：提供全局代理、直连、绕过局域网与大陆等模式；支持域名、IP/CIDR、端口、协议嗅探规则，以及优先级的拖拽排序。Windows 进程名分流放到后续，不通过在 IR 里加字段来冒充已经支持。
【v1.3 裁定 Q-A=A】本条原文继续有效：P0 不做进程分流，IR 不预留进程字段。已记录的事实：固定核心 `676eaf6` 本身支持路由规则的 `process` 条件，Windows 系统代理模式下不需要 TUN 就能按进程分流；但服务账户的权限、查找失败时规则静默不命中、查找开销这三点都未实测。P1 的「本地入站进程分流」以此为起点；首个 Windows 版本可用、PC-10 权限实测有结论后，再决定是否提前。以后开放 `process` 条件时，桥的路由白名单必须显式纳管（目前 `route_control.go` 的 `validateProfileRoutes` 不拦截该字段，只是 IR 生成不出来），查找失败必须可见。详见 `2026-11-23-pCryoxy-REQ14进程分流与服务权限裁决资料-zhn-tbxg2iah-win.md`。

REQ-15：Geo 是独立、可版本化的数据包。首次交付就提供基本数据，不能要求先联网更新才能用基础分流。基本集合覆盖 `geoip:private`、`geoip:cn`、`geosite:cn`、`geosite:geolocation-!cn`，以及广告分类所需的数据；具体分类名、下载源、许可和裁剪方式要核验，不预设任何数据源里一定存在 `category-ads`。

REQ-16：Geo 的后续更新只能由用户主动触发，从网络下载；参考 v2rayN 的用法，但不复制其源码；不自动定时下载。支持完整性校验、失败回滚、生效状态反馈，以及原始需求中的 .gz 输入。下载、替换、加载三种状态分开；原生 geodata 或控制面下载由蓝图确定，不能把文件覆盖当成已经生效。

## 6. 固定发行版、升级与回退

REQ-17：固定兼容的 Xray 发行版并记录源码基线，不持续跟随 main（当前固定 `676eaf6`）。应用声明支持的核心版本范围；核心发行版升级后可以支持新版本，也能回退。默认使用稳定版；预发布渠道是原始需求里的显式可选项，不默认自动安装。【v1.3 G-03】由 PC-13 承接：预发布渠道默认关闭，由用户显式开启；PC-13 提出准入和兼容门槛，人类确认后冻结。

REQ-18：Windows 的核心独立存储、独立更新；自动检查更新，由用户确认后安装。校验 SHA256 和兼容性，保留上一套可用的内核及对应的配置快照；启动验证失败时自动恢复，也支持手动回退。原子切换、恢复验证和真实性验证要分开设计，仅校验摘要不能保证发布者身份。

REQ-19：Android 先直接分发签名 APK，内核随应用包更新，不套用桌面端「下载后执行二进制」的方案。核心回退通过版本号更高、内含旧核心的新 APK 交付，不承诺直接降级安装旧 APK。回退时要验证应用、旧核心与配置/数据的兼容性，明确是生成兼容配置还是恢复快照；APK 安装成功不等于回退成功，也不承诺桌面式的自动回退。应用、核心、Geo 的版本分别记录；版本管理分开，不等于每个平台都能单独替换核心。任何需要清空用户数据、卸载重装或缩减功能的方案，都要另行裁决。

## 7. 性能统计口径

REQ-20：应用本体不包含 Xray-core、sing-box、Mihomo 等代理内核，也不包含独立的 Geo 数据包；应用本体小于 10MB 是设计目标，不是已验证的结果。不得用模糊的统计范围宣称完整产品小于 10MB。

REQ-21：交付时分列应用本体、内核、Geo、其他运行依赖、完整下载量和安装占用。系统 WebView 等依赖怎么统计必须说明；Android 即使核心在 APK 内，也要报告 APK 实际总大小和内核分项，不能把逻辑上的拆分说成可以分别安装。

REQ-22：冷启动分别测首帧、可交互、代理就绪三个时间点；内存包括应用、WebView、核心、VPN 服务和 Geo 加载等实际开销。在并发探测和实时流量刷新时，UI 要保持响应。具体设备、节点规模、刷新频率、P95/P99 和数值预算，在蓝图和原型测试之后冻结（【v1.3 G-04】PC-15 结束时设「性能基线测量」里程碑，测量结果交人类冻结预算，PC-16 按冻结后的预算验收）；包体的排除项不适用于真实运行内存。

## 8. AI、安全与编码铁律

REQ-23：首期纯本地，没有账号和云同步；凭据由平台安全存储保护；日志脱敏，不记录完整的节点凭据和订阅令牌；导出含凭据的内容时明确提示（【v1.3 G-02】由 PC-14 提供两通道统一的导出命令，PC-15 提供导出页；含凭据时二次确认，默认导出不含凭据）。AI 不在关键路径上，兼容 OpenAI 风格接口和本地 Ollama；P1 工具包括状态查询、分流规则、链接导入、策略组、测速、诊断，高危操作要二次确认，凭据默认不发给模型。AI 出故障不能影响代理。「纯本地」指首期没有产品账号和云同步，配置主要保存在本地；不排除 P1 用户主动配置远程 AI 接口。发送哪些字段、怎么脱敏、授权边界在哪，由蓝图明确；本文不授权把节点凭据外发。

## 9. 本地访问日志（原 v1.2 增量）

**状态：REQ-33～36 及 6 项默认值已由人类 2026-11-23 18:17 确认（§13 G-06）。PC-21a 的「需求未确认」门槛解除，认领仍须满足卡面依赖。本节内容与 v1.2 增量相同，只增加了 REQ-33 的 Android 澄清。**

REQ-33：Windows 和 Linux 运行形态必须提供本地结构化访问日志，至少能查询：访问时间；域名级的访问目标、SNI、目标 IP 和端口；使用的策略组；最终选中的节点；节点重试和故障转移链；DNS、连接、握手、首字节和总耗时；上传/下载字节数；真实流量的平均速度；成功、失败和安全错误码；能确认时的来源应用/进程标识。无法确认来源应用时必须写 `unknown`，不得根据目标域名或端口猜测应用。
【v1.3 澄清】Android 不提供访问日志页面。PC-15 按平台能力隐藏日志入口，并提示「此平台不提供访问日志」，不显示空页面。

REQ-34：日志必须支持：按天数保留；按总容量限制；按日期或大小滚动；启动时三种清理策略（不清理、只清理过期日志、删除上次启动之前的日志）；服务重启后继续写入；清理和写入结果可查询。默认保存天数、默认总容量和目录由实现卡提出、在契约中冻结，不能在实现中静默决定再当成用户裁定。已确认的默认值：保留 7 天；总容量 1 GiB；启动时只清理过期日志（`expired`）；只记录元数据；不做实时 tail；Web 只绑定 127.0.0.1。日志目录由 PC-10（Windows）和 PC-19（Linux）冻结。

REQ-35：日志默认只记录域名级元数据，默认不记录 HTTPS 完整 URL 的 path 和 query、请求正文、请求头、Cookie、Authorization、订阅 URL、节点凭据、ticket、SecretRef 或原始核心配置。完整 URL、TLS 解密和 MITM 不属于 P0。日志是本地敏感数据，不能进入 AI 上下文、第三方遥测或崩溃自动上报。`SafeEvent` 仍是通用安全事件白名单；访问日志使用独立的本地鉴权投影，不能通过扩大 SafeEvent 字段来绕过脱敏边界。

REQ-36：内置 Web 管理端必须支持在本机查看和筛选 Windows/Linux 日志，提供策略组、节点、延迟、速度、流量、状态和来源应用等查询维度，支持日志导出和受控清理。默认只绑定 `127.0.0.1`；非回环监听必须显式配置管理员 Token，缺 Token 拒绝启动；Token 不得出现在 URL、日志、响应、静态构建物或浏览器持久化中。

对既有需求的关系（原 v1.2 §2）：REQ-09「吞吐测速只能由用户主动触发」继续有效，REQ-33 的速度是对真实代理流量的被动统计；REQ-35 是 REQ-23 日志脱敏要求下的受控例外；REQ-28 的「流量查询」扩展为「访问日志的查询、统计、导出和受控清理」；Windows TUN/进程分流仍属后续能力，REQ-33 只要求能确认的来源字段和 `unknown` 降级。

## 10. Linux、独立 daemon 与 Web 管理端

REQ-25：【v1.3】已并入 REQ-03，编号保留，不再使用。

REQ-26：核心 IR、调度器、测速和 Xray 桥接不能强依赖 Tauri 窗口；提供可独立编译、无界面运行的 `pcryoxy-daemon`。GUI 是控制端，不是核心生命周期的唯一宿主。

REQ-27：Linux 支持 systemd 常驻服务；Windows 支持原生 Windows Service、开机自启和无桌面登录运行。服务的停止、重启、崩溃恢复、升级回退、日志和退出码必须定义，不能把 GUI 进程退出等同于核心停止。

REQ-28：daemon 内置 HTTP/WebSocket 服务，托管 SolidJS 构建产物 `dist/`；用浏览器就能完成配置、策略组切换、测速、实时状态和流量查询（含 REQ-36 日志）。Web 控制面复用已有的公开 DTO、revision、operation、SafeEvent 约束。

REQ-29：`ui/src/api/` 为同一套 SolidJS 前端提供 Tauri IPC 和浏览器 HTTP REST + WebSocket 两种传输适配；业务 DTO、错误、操作票据和事件语义保持一致，不在前端复制两套业务逻辑。

REQ-30：默认只绑定 `127.0.0.1`。显式监听 `0.0.0.0` 或其他非回环地址时，必须强制校验管理员 Token；禁止匿名管理，禁止把凭据放进 URL、日志或前端持久化。

REQ-31：Linux 使用权限为 `0600` 的密钥文件或 Secret Service；Windows Service 账户必须明确凭据归属、ACL 和轮换/失效处理；服务账户不能默认读取交互用户的私有目录。
【v1.3 裁定 Q-B=A】Windows 主服务坚持最小权限，不以 LocalSystem 运行。以后需要特权（例如 P1 的 TUN 建网卡、改路由），由一个独立的特权组件承担：只接受本机 IPC，只处理固定的几类请求；它的契约和依赖届时另行申请。PC-10 现在就要在设计里写明「服务身份变更时主密钥的重新封装和迁移路径」，P0 只要求设计和测试用例，不要求实现账户切换。

REQ-32：Linux 的 tun、SOCKS/HTTP 入站、systemd 资源和路由设置，必须把无需特权的控制面和需要授权的数据面分开；桌面 Web UI 不能假设存在桌面组件，软路由部署不以安装 WebKitGTK 为前提。
