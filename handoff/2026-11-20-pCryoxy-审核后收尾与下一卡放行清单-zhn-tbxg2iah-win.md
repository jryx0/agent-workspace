# pCryoxy 审核后收尾与下一卡放行清单

- 项目: pCryoxy
- 版本: v1.0
- 发布状态: 待 WorkBuddy 审核后作为共享协作清单
- 编制: workbuddy@zhn-tbxg2iah-win~zhn-x-w｜2026-11-20
- 适用输入: 需求基线 v1.1、工程蓝图 v0.3、实施任务卡 v1.1、API Spec v1.1
- 目的: 将“审核结论”闭环为“可追溯、可同步、可认领、可复核”的项目状态，避免同一张卡因记录、基座、版本或证据缺失反复返工。

## 一、核心原则

1. **审核结论、代码状态、共享登记、远端状态必须同时闭环。** 只改其中一项，不得放行下一卡。
2. **通过不等于合并。** WorkBuddy 可以审核通过，但代码合并由代码仓所有者按项目规范执行；必须明确当前集成基座。
3. **文档版本必须可追溯。** 下一卡只能使用统一入口指向的正式版本，不得使用仅本机草案或旧版本。
4. **未验证能力不得写成支持。** 构建、源码核验、合同测试、真实互通、真机、服务生命周期分别记录，不互相替代。
5. **一项缺口只建立一个返工清单。** 返工交付必须逐项回应原退回项，不重复解释已关闭问题，也不得扩大范围。

## 二、审核方收到交付后的固定流程

### A. 先锁定审核对象

- [ ] 卡ID、项目名、认领人、设备名、分支、worktree、commit 全部一致。
- [ ] 交付 commit 可从分支和远端引用独立定位；不是口头 commit 或未提交工作区。
- [ ] 文件清单只包含卡面允许文件；公共 Cargo/lock/proto/DTO 是否越权已核对。
- [ ] 输入文档版本写明并能从共享入口到达。
- [ ] 本卡没有代认领下一卡、代标 done 或代提交审核记录。

### B. 对照卡面逐项验收

对每一条“动作”和“真实验收”分别记：通过 / 退回 / 外部条件阻塞 / 未覆盖。

- [ ] 功能行为：检查真实入口与边界，不只读实现者总结。
- [ ] 错误行为：检查错误码、失败不变、未知结果和回滚语义。
- [ ] 数据边界：检查秘密、日志、事件、DTO、序列化和持久化路径。
- [ ] 依赖边界：检查新增依赖、锁文件、生成物、所有权和许可证说明。
- [ ] 平台边界：Windows、Android、Linux、无桌面、服务账户等按卡要求分别核验。
- [ ] 版本边界：检查 app/API/bridge/core/platform/arch/libc 组合，不用“能编译”替代兼容性。

### C. 证据分级

- [ ] 源码核验：确认实现路径和文件归属。
- [ ] 静态检查：fmt、clippy、类型检查、秘密扫描等有命令、退出码和环境。
- [ ] 合同测试：测试运行器真实执行目标测试，不能只有 0 tests。
- [ ] 集成测试：真实服务、真实核心或受控网络路径，不能只用 Mock 代替。
- [ ] 平台测试：真机、systemd、Windows Service、无桌面环境按需提供证据。
- [ ] 性能/包体：报告测量口径、设备、节点数、P95/P99；未冻结预算不自造合格线。

## 三、通过时必须完成的收尾动作

### 1. 追加审核结论到交接文档

审核结论追加到交接文档末尾，不改写执行方原交接内容。必须包含：

- 审核人、设备、时间、卡ID；
- 审核对象 commit、分支和基座；
- 审核结论：通过 / 退回 / 受外部条件阻塞；
- 已核对的测试证据及“执行方实测/审核方独立重跑”的区别；
- 未覆盖项和不代表通过的范围；
- 下一卡是否放行；
- 若通过，明确指定集成基座和正式输入版本。

### 2. 追加项目登记状态

在 `memory/projects/<项目>.md` 末尾 append-only 追加：

```text
[@workbuddy @<设备与账号> <时间>] 【复审通过】项目：<项目> | <卡ID> | done |
commit=<完整commit> | 交接=<共享文件> §<节号> |
证据=<测试/平台证据摘要> | 下一卡=<卡ID/不放行> |
集成基座=<commit或明确“待代码所有者合并”> |
输入版本=<基线/蓝图/任务卡/API Spec>
```

退回或阻塞时保留原状态行，追加新行，不改旧记录。`done` 只表示本卡验收结论，不表示全项目发布完成。

### 3. 明确代码集成基座

必须三选一并写入交接和项目登记：

- **已集成**：目标分支包含审核通过 commit，并给出合并/快进 commit；
- **待集成**：审核通过 commit 是下一卡指定基座，但项目 main 尚未包含，写明由谁合并；
- **不可集成**：存在冲突、依赖未冻结或主干条件不满足，下一卡不得认领。

没有这三项之一，不得输出“下一卡可开工”。

### 4. 校验正式文档版本与路径

- [ ] 统一入口的文档表已更新到当前版本。
- [ ] 需求基线、蓝图、任务卡、API Spec 版本互引一致。
- [ ] API Spec 继承关系明确：修订版必须说明是“旧版全文 + 增量”，不能只留下增量片段。
- [ ] DTO、生成源、生成输出、Tauri/REST/WS 适配路径写到文件级别。
- [ ] 旧版本标为历史基线，不能与当前版本并列为可维护正文。
- [ ] 任务卡新增或调整的卡号、依赖、文件所有权和并行窗口已登记。

### 5. 共享仓提交与同步

- [ ] 获取 Git 写锁，确认无压缩锁和 index.lock。
- [ ] `fetch` 后确认本地与远端基线，避免覆盖并发提交。
- [ ] 只 `git add` 本轮明确文件，禁止 `git add .`、stash、autostash、强制重置。
- [ ] 对新增/修改文件做 gitleaks 或等效秘密扫描。
- [ ] 提交信息包含项目和动作；记录完整 commit。
- [ ] 分别推送 origin 与 backup；不得只推一个远端后宣称完成。
- [ ] 独立核对 `HEAD == origin/main == backup/main`。
- [ ] 其他 agent 改动数量和路径保持原状，并写入最终反馈。

## 四、退回时必须一次性给全返工单

退回不得只写“请修复”或只贴测试失败。返工单必须一次包含：

| 字段 | 要求 |
|---|---|
| 问题编号 | R1、R2……稳定编号，后续复审沿用 |
| 证据 | 文件、函数、测试、命令或具体行为 |
| 影响 | 违反哪条卡面/契约/用户裁定 |
| 最小修复 | 允许修改的文件和禁止扩大的范围 |
| 复审测试 | 测试名称、输入、预期结果 |
| 交付格式 | 新 commit、交接路径、实际命令/退出码 |
| 下一步 | 保持 doing、blocked 或允许进入复审；不得自行 done |

返工复审只逐项关闭 R 编号；新增问题另编号，不把新需求混入旧卡返工。

## 五、下一卡放行前的八项门禁

下一卡收到提示词前，WorkBuddy 必须确认：

1. [ ] 前置卡在共享项目记忆中有正式审核记录；
2. [ ] 审核记录已进入提交并同步 origin/backup；
3. [ ] 前置卡 commit 与集成基座关系明确；
4. [ ] 当前任务卡、API Spec、蓝图为统一入口指向的正式版本；
5. [ ] 依赖卡状态全部满足，todo 不被误当作可并行；
6. [ ] 前置卡未遗留未关闭的 R 编号；
7. [ ] 新卡的公共文件所有权、生成源和锁文件所有者明确；
8. [ ] 新卡提示词已写清“不做什么、实际证据、交付格式、禁止自称通过”。

任一项不满足：只给“准备/只读核对”提示，不给“认领并开工”提示。
