## 三、任务卡

### RL-004｜统一协作入口中的版本、步骤数与验收状态

**目标**：使全局规范、平台指令模板、执行保障文档、新 Agent 接入提示和近期交接对“当前版本、10 步自检、注入/验收状态、L1/L2/L3状态”的描述一致。

**范围建议**：先做只读差异清单，至少核对 `global/rules.md`、`env/execution-enforcement.md`、`env/project-AGENTS-hook.md`、`env/new-agent-bootstrap.md`、最新相关 handoff；区分规范版本、模板版本与部署/粘贴/验收状态。仅在获人类批准后更新文档。既有 `memory/org.md` / handoff 为 append-only，不回改旧记录；当前 prnmgt 未提交改动不在本卡范围内。

**验收标准**：
1. 交付一份逐文件差异表，标明现值、目标值、事实依据和拟改动作。
2. 不把规范版本号误当作注入或验收状态；每个入口明确权威来源与“已验证/未验证/未知”。
3. 若获批修改，所有现行入口的步骤数与规范一致（第八节 10 步）；运行 `env/rules-lint.sh` 并报告结果。
4. 不覆盖历史记录，不触碰他人未提交改动；未获批时仅交差异清单，不改规范或注入设置。

### RL-005｜跨设备任务认领防竞态

**目标**：评估当前 append-only 任务认领在两个设备并发开工时无法原子互斥的问题，提出最小可行且可审计的跨设备防撞方案。

**范围建议**：先研究共享仓 Git 同步模型、离线/网络不可达、同一任务并发认领、认领过期/释放、冲突回滚与人类裁决；比较可用方案（例如任务唯一认领文件/原子创建、专门协调服务或明确的 fail-closed 人工确认），不得预设外部服务或新增依赖。方案确认前不改现有任务登记格式，不实现锁服务。

**验收标准**：
1. 提供威胁/竞态场景表，至少覆盖“两设备同时认领”“离线旧快照”“同步冲突”“执行者异常退出”。
2. 提供推荐方案、替代方案、失败行为与恢复步骤；明确防撞键仍为“项目 + 任务ID”，账号仅定责。
3. 给出可重复的并发演练与通过/失败判据；证明失败关闭，不因锁不可用而默认放行。
4. 任何需新增工具、依赖、服务或改规范的方案，先提交人类批准，不先行实施。

### RL-006｜自检与门禁实际状态核验

**目标**：区分规范要求、文档设计与各 Agent/设备上实际启用且验证通过的机制，消除把“方案已写”误报为“控制已运行”的风险。

**范围建议**：按 Agent 软件 × 设备整理 L1 注入、首次注入验收、L2 SessionStart 凭证/抽查、L3 PreToolUse 门禁状态；只做只读核验或请求人类提供 UI/运行证据。未经批准不改平台设置、不启用钩子、不安装依赖。

**验收标准**：
1. 交付矩阵，状态只用“已验证、未验证、未启用、不适用”，每项附证据日期与来源；无证据写“未知/未验证”，不得推断通过。
2. L1 验收覆盖 T0/T1/T2 分级与 T2 10 步简报；L2 检查凭证字段是否含档位、依据与检查结果；L3 标记是否实际启用及探针/只记录/拦截阶段。
3. 识别跨 WorkBuddy、trae 等入口覆盖边界，并列出未覆盖风险及人工补偿措施。
4. 若需变更，另行取得人类批准；不将审计建议写成已部署事实。

### RL-007｜按场景加载与 token 成本优化

**目标**：在不降低安全、并发隔离、审计或治理要求的前提下，减少无关规范、记忆和简报的重复加载。

**范围建议**：基于 RL-004 对齐后的现行文档，统计常见 T0/T1/T2、单项目/多项目、只读/写入场景的必要读取集合和重复内容；提出按任务触发的步骤清单、精简简报格式、规范状态单一来源等优化，不自行删减红线或绕过审计。

**验收标准**：
1. 给出至少 3 类典型场景的“现状 vs 建议”加载清单及估算依据；不以未经测量的数字宣称节省比例。
2. 保留所有 T2 必需检查、挂起防撞、凭据/密钥边界、代理/双远端推送核验与异常 fail-closed 行为。
3. 明确唯一事实源，避免把完整规则复制到多个入口；建议与 L1 1500 字符上限兼容。
4. 提供不改变规则语义的试运行/回归验收方案；需改规范或平台指令时先获人类批准。
