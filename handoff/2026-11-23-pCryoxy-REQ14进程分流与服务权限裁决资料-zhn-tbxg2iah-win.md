## 1. 固定核心的进程匹配能力（源码事实）

| 项 | 事实 | 出处（676eaf6） |
|---|---|---|
| 配置字段 | 路由规则 JSON 字段 `process`（字符串列表），编译进 `RoutingRule.Process` | `infra/conf/router.go:157,268`；`app/router/config.go:113` |
| 匹配写法 | 进程名（自动去掉 `.exe`）、绝对路径、以 `/` 结尾的目录前缀、`self/`（Xray 自身）、`xray/`（Xray 可执行文件路径） | `app/router/condition.go:300-340` |

| Windows 实现 | `GetExtendedTcpTable/UdpTable` 按源端口找 PID，再 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`＋`QueryFullProcessImageName` 取路径 | `find_process_windows.go:235,243` |
| Linux 实现 | 读 `/proc/net/{tcp,udp}[6]` 找 socket inode，再遍历所有 `/proc/<pid>/fd` 找属主，读 `/proc/<pid>/exe` | `find_process_linux.go:34-181` |
| Android | 必须由宿主注册查找函数，否则直接报错 | `find_process_android.go:15-19` |
| 其他平台 | 不支持 | `find_process_others.go` |
| 查找失败时 | 只记一条错误日志，规则按**不命中**处理，流量走后续规则 | `condition.go:373-378` |

**对产品的含义**

- Windows 系统代理模式下，浏览器这类遵从系统代理的程序，会从 `127.0.0.1` 连进本地入站，源端口对应的 socket 归这个程序所有，所以能按进程分流，不需要 TUN。
- 不遵从系统代理的程序根本不会进入 Xray，按进程也分不到。这部分才需要 TUN 接管，P1 的「Windows TUN」仍然成立。
- REQ-33 的「可确认时的来源应用/进程标识」可以复用同一套查找机制。PC21 卡 §7 把它列为后续增强，两件事可以合并考虑。

## 2. 需要实测的限制（目前都没有证据）

1. **权限**：PC-10 设计的是低权限服务账户（独立账户或服务 SID）。用这种账户对其他用户的进程、尤其是提权进程调用 `OpenProcess`，可能被拒；被拒时拿不到进程名，规则就不命中。Linux 下低权限 daemon 读不了其他用户的 `/proc/<pid>/fd`，结果也一样，除非给 root 或 `CAP_SYS_PTRACE` 一类能力，而这又和最小权限冲突。
2. **隐性失效**：查找失败时规则不命中，而不是报错。用户以为「某程序走直连」，实际上它可能走了默认代理（反之亦然）。如果要做，必须让失败可见（日志或状态里能看到「进程未识别」），否则违反「不静默」原则。
3. **性能**：只有规则里带 `process` 条件、且这条规则被评估到时才会触发查找。Linux 每次要遍历所有进程的 fd；Windows 每次要拉一整张连接表。连接多的时候开销要实测。
4. **桥的现状**：`native/xray-bridge/route_control.go:27-56` 的 `validateProfileRoutes` 只拦未知字段、脚本和 webhook，**不拦 `process` 字段**。目前 IR 的 `Match`（`crates/core-ir/src/routing.rs:98`）没有这个字段，所以这条路径走不到。以后如果开放，桥白名单要显式纳管，不能靠「IR 生成不出来」兜底。

## 4. 服务权限：三个方案

**事实**

- Wintun 创建虚拟网卡需要管理员或 SYSTEM 权限。固定核心在 Windows 上的 tun 依赖 `wintun.dll`，PC-04b H1 已在 Windows 构建中拒绝 tun。
- PC-10 当前设计（蓝图 v0.3 L135、任务卡 v1.1 PC-10）：服务用独立账户或服务 SID，配 ACL；管理员授权注册；主密钥要在服务身份下重启后仍可读，不借用登录用户的凭据库。
- 同一个服务进程里还跑着订阅解析、Web 管理端（REQ-28，可能监听非回环地址，REQ-30），P1 还要加 AI 工具调用。
- 系统代理是按用户设置的，服务本身设置不了，要靠「交互用户代理」去设。

| 方案 | 内容 | 好处 | 代价 |
|---|---|---|---|
| **A 最小权限＋独立特权组件（推荐）** | 主服务保持低权限。将来 P1 做 TUN 时，另做一个只负责建网卡、改路由的小组件，以 SYSTEM 运行，只接受本机 IPC 和固定的几种请求 | 订阅解析、Web 管理端、AI 出漏洞时，影响范围限于低权限账户 | P1 多一个组件和一份 IPC 契约 |
| B 现在就用 LocalSystem | 服务直接以 SYSTEM 运行 | P1 加 TUN、进程查找时不用改账户 | 上面这些面向外部输入的模块全部以 SYSTEM 运行，任何漏洞都等于整机被控；也违背 REQ-31「服务账户不能默认读取交互用户私有目录」的本意（SYSTEM 什么都能读） |
| C 现在低权限，P1 再整体提权 | 等需要时再把账户改成 SYSTEM | 现在不用多做 | 最大的隐性成本：DPAPI 主密钥和账户绑定，换账户就要迁移密钥；而且最终还是落到 B 的风险上 |

workbuddy 建议：**选 A**，并在 PC-10 卡面增加一条设计要求：写明「服务身份变更时主密钥的重新封装和迁移路径」，P0 只要设计和测试用例，不要求实现账户切换。无论将来选 A 还是 C，这一条都用得上。
