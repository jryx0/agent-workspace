## 2. 一致性问题与处理

| 编号 | 原问题 | 影响 | 同步处理 |
|---|---|---|---|
| C-01 | 需求有“流量查询”和 Web 管理端，但没有访问日志、保留和清理语义 | 无法定义实现范围和验收 | 新增 REQ-33/34/36、PC-21、API 日志 DTO/命令 |
| C-02 | 既有 SafeEvent 禁止敏感字段，而用户要求访问网址和应用来源 | 容易把域名/进程信息直接塞入通用事件或 AI | 将 `AccessLogRecord` 与 `SafeEvent` 分离；默认域名级、本地鉴权查询 |
| C-03 | API 只有 traffic 事件，没有历史日志查询 DTO | Web 只能看实时状态，不能查历史 | 新增 `logs_query`、`logs_stats`、设置、清理和导出命令 |
| C-04 | REQ-09 禁止后台主动吞吐测速，用户又要求速度 | 可能误把定时测速加入 P0 | 明确速度是实际代理流量的被动统计；主动高级测速仍为 P1 |
| C-05 | 现有任务卡 PC-20 负责 Web，而没有日志存储所有者 | 容易由 PC-20 直接读文件或与 PC-18 争写 | 新增 PC-21 负责日志域/存储；PC-20 只做 HTTP/WS/auth/页面适配 |
| C-06 | Windows TUN/进程分流是 P1，用户要求知道哪个程序发起 | 容易把进程识别伪装成 P0 已支持 | P0 只要求可确认来源或 `unknown`；WFP、UID/cgroup/eBPF 为后续增强 |
| C-07 | PC-04 Runtime ABI v2 已形成提交但仍待 WorkBuddy 复审 | 日志源事件不能写成已经接入生产 daemon | 在 PC-21 依赖中标为待复审；不改变 PC-04/PC-18 blocked |
| C-08 | Windows/Linux 服务目录和权限尚未完成实测 | 日志目录、ACL、服务重启语义未冻结 | 由 PC-10/PC-19 提供平台证据，PC-21 只约束最小权限和接口 |
| C-09 | 原需求基线 P0 为 Windows/Android/Linux，前文还讨论 iOS/鸿蒙 NEXT | 容易把跨移动端统一日志或分流提前纳入 P0 | 本增量只新增 Windows/Linux 日志；iOS/鸿蒙 NEXT 不纳入本卡 |

## 4. 需求边界结论

### 已纳入 P0 任务设计

- Windows/Linux 本地结构化日志；
- 策略组、最终节点和节点切换链；
- 延迟、实际流量速度和字节数；
- 保存天数、容量上限和启动清理；
- Web 历史查询、统计、导出和受控清理；
- 回环默认监听和非回环 Token 强制；
- 日志脱敏、权限和服务重启恢复。

### 明确不纳入本次 P0 承诺

- HTTPS 完整 URL path/query、正文或 TLS MITM；
- 远程公网日志管理；
- 自动上传日志；
- 三端跨平台完全相同的应用识别；
- 仅凭 TUN 绝对识别原始进程；
- Windows TUN/进程接管；
- Android/iOS/鸿蒙 NEXT 日志实现。

## 5. 仍需用户确认的产品决策

以下是实现默认建议，不冒充已经裁定：

1. 默认保存天数：建议 7 天；
2. 默认总容量：建议 1 GiB；
3. 默认启动清理：建议 `expired`，而不是删除全部历史；
4. 默认详细级别：建议 `metadata`；
5. 默认实时 tail：建议不列入 P0，先做历史查询和统计；
6. 默认 Web 监听：`127.0.0.1`，不开放远程访问。

若用户不另行裁定，实施卡只能将这些写成可配置的实现默认，不能写成产品永久固定值。
