# Vault / IR 事务边界

## 契约范围和角色

- 已冻结 `plugin-sdk::SecretStore` 只暴露 `put` 和 `with_secret`；本说明不修改 trait、DTO 或 API Spec。`with_secret` 仅限受信任本地后端，不作为 IPC getter；任何附加 staging 操作只属于 PC-03 的内部实现接口，不是公共管理 API。
- PC-03 实现密钥与加密文件、不可变或等价可恢复的 vault 候选、认证校验、受限暂存/提交/清理与失败保留；其本地 `commit_staged` 只代表 vault 候选达到约定的持久状态，不独自代表 IR 和 vault 已联合提交。
- 后续受信任单写者协调器负责串行化导入及预期 revision 检查、编排 vault 与 IR 的一致发布、崩溃恢复及最终清理。PC-06 负责解析/订阅和校验，不能自行绕开协调器发布 IR；持久协调器不是 PC-03 本卡已实现的能力。
- `SecretRef`、凭据、完整输入及第三方错误原文不进入公共 DTO、日志、事件或网络输出。内部事务记录放在私有受控存储中，外部只返回白名单错误码和安全状态。不要在锁内等待网络或跨 await 持有 vault 锁。

## 建议执行顺序与提交点

1. 单写者以 operation ID 与 expectedRevision 接受一次意图；保存私有的旧已提交状态及事务标识。必要的授权、路径/属主/权限和密钥可用性检查失败时直接拒绝，不修改当前 vault 或 IR。
2. PC-06 对输入解析及唯一语义校验；由 PC-03 将新的秘密写入独立候选，产生仅供受信任后端使用的引用及 HMAC credential_id。暂存不得覆盖旧密钥、旧密文、现有 alias 或旧已提交 vault；冲突和失败丢弃候选或留待恢复清理。候选明文仅局部存在。
3. 锁外准备完整 IR 候选及 vault 候选，验证候选中的所有秘密引用可在对应 vault 版本解析，确保旧状态仍可用。按平台持久化并校验两份候选；未完成的文件绝不能被读取方当作已提交版本。
4. 短的单写者提交段重新核对 expectedRevision；先使 vault 候选完整可恢复、再通过一次原子且持久的**私有 active manifest/提交指针**发布关联的 IR 快照和 vault 版本。所有重启恢复和配置读取须从同一个已提交指针解析这对版本；单独覆盖两个活跃文件不满足此约束。各平台需实现并测试文件同步、目录同步或等效持久化语义；若不能保证则显式报不支持或失败。
5. 已提交指针持久化确认后才返回成功、发布事件；处理中的读者可继续持有旧版本。旧版本、被替换的秘密及暂存清理要在没有任何已提交快照、在途读者或未决事务引用时执行，不得抢先删除；失败记录可重试的清理状态，不泄漏秘密。

上述是适配已有单写者的受限提交协议方案，不要求引入通用分布式事务框架。具体文件格式、manifest 所属模块及平台原子替换/持久化原语仍须相应实现卡与 WorkBuddy 审核；当前仓库尚无该协调器，PC-03 不得声称已实现跨 vault/IR 的崩溃原子性。

## 失败和恢复

| 阶段 | 处理与可见状态 |
|---|---|
| 校验、暂存、加密或候选写入失败 | 返回明确安全错误；已提交指针、旧 vault、旧 IR 不变；仅清理本事务创建的未提交候选。 |
| revision 冲突 | 不发布候选；返回冲突；禁止覆盖其他已提交更新。 |
| vault 准备完成、IR 准备或提交失败 | 活跃指针仍指向旧版本；保留旧 vault；隔离未提交候选并在确认无引用后清理。 |
| 指针写入或持久化结果未知 | 不返回成功或假设回滚；返回结果未知并保留旧/候选及恢复记录，禁止清理；以 operation ID 查询和启动恢复来确定实际提交结果。 |
| 进程中断 | 启动时先取得单写者所有权、验证已提交指针对应的两份完整版本，再决定启用；发现未提交候选仅在确认未被任何已提交版本引用后清理。指针损坏、密钥不可用、校验失败时明确报未就绪，不覆盖现有密文。 |
| 已提交后清理失败 | 已提交状态仍为实际结果；记录安全错误/待清理状态，不回报为未提交；保留候选直到安全回收条件成立。 |

必须使用实际平台故障注入和进程重启验证写入边界、断电/中断恢复、结果未知、旧引用可读和仅清理本测试资产；Android 真机、Windows 服务身份与 ACL、Linux 异账户仍需各自证据。此说明不替代这些验证，不构成它们已通过。
