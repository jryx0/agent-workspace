# 多设备多 Agent 协同工作架构与规范 (v2.2)

> **致所有 Agent：** 你现在接入了一个跨设备（Windows/Linux/iOS/Android/HarmonyOS）、多 Agent 协同的个人/团队工作空间。请严格遵循本规范进行文件读写、记忆存储、工具调用和任务交接。如果你是人类用户，请按此文档进行环境初始化。

## 〇、 规范发现与注入（v1.8.5 新增，最高优先级）

> **背景**：本规范只存放在 `~/.agent-shared/global/rules.md`，**不会自动进入 Agent 会话上下文**。会话启动时若未注入，Agent 无从知道规范存在，第八节自检也不会执行——2026-11-05 某会话未加载任何版本规范即执行 `npm install -g wrangler`，根因即此机制缺陷（调查见 `memory/org.md` 09:08 条目）。

- **① 注入通道（人类负责配置，按可靠性排序）**
  1. **平台全局指令（必配）**：WorkBuddy 桌面版「左下角头像 → 设置 → 个性化 → 给 WorkBuddy 的指令」（旧名：自定义指令，≤1500 字符），**每个新会话自动注入**。内容只放短红线（模板见 `env/project-AGENTS-hook.md` A 段）：开工前读本规范并执行第八节自检；装工具前跑 `tools-scan.sh --check`；禁全局安装；改 `~/.agent-shared` 后 10 分钟内 commit + `git sync`。
  2. **项目规则文件（项目级补充）**：工作区根目录 `AGENTS.md` / `CODEBUDDY.md`（打开项目自动读取）。
  3. **用户级规则目录 / 技能**：长文本按需加载，**不得替代 ①② 的必读入口**。
  > **多账号（v2.1，见 三-8）**：平台全局指令须**每个账号各配一次**；新账号接入必须先做 〇④ 首次注入验证，未注入账号的会话按 〇③ 停写上报。账号标识只用于定责，不参与任务防撞。
  > **配套模板清单（v1.8.9 补登，均只放指针、不放规范正文）**：`env/project-AGENTS-hook.md`（A 全局指令模板 / B 项目挂接块 / C 验证清单）、`env/new-agent-bootstrap.md`（新 Agent 一次性开场提示词）、`env/execution-enforcement.md`（执行纪律保障方案，含现行强化版全局指令全文）、`env/handoff-suspended-template.md`（挂起任务登记模板，见 三-4，v1.8.10 补登）；另有只读工具 `env/proxy-check.sh`（代理与双远端核对，见 五-1 / 八-10）。现行实际平台指令以 `env/execution-enforcement.md` 二-L1 为准（**v2.0 起为分级版**）。
- **② 项目挂接（硬性）**：`~/source/` 下每个项目的 `AGENTS.md` / `CODEBUDDY.md` 必须在「开工前必读顺序」**首项**写明全局规范路径与「先读并执行第八节自检，再读本项目文件」；挂接块模板见 `env/project-AGENTS-hook.md` B 段。未挂接的项目视为**接入未完成**，登记进 `memory/projects/<项目名>.md` 并提醒人类；agent **不得擅自改写项目规则文件**，改动必须走 三-6 worktree + `agent/*` 分支，待人类合并。
- **③ Agent 侧兜底（无注入时）**：任何会话在涉及**文件写入、环境配置、代码、工具/依赖安装、Git 写操作**之前，若上下文中没有本规范全文或指针，必须自行 Read `~/.agent-shared/global/rules.md`；读不到则**停止写操作并报告人类**。不得以「用户没提规范」「任务很小」为由跳过档位判定。**T0 例外（v2.0）**：纯对话／只读会话不触发本兜底，但一旦转入写操作立即按 〇⑦ 重新判定；T1 仍须遵守 〇⑦ ③ 最小红线集。
- **④ 首次注入验证**：配置全局指令后，人类新开一个任务发「开工前按规范自检」；agent 应主动读本规范并跑 `tools-scan.sh --check`。未做到即注入失败，检查指令是否保存、是否为新任务（指令只在会话开始时注入，当前会话不会重新加载）。**该显式自检要求按 〇⑦ 强制判为 T2，不受 T0「纯对话」判定影响**（v2.0）。
- **⑤ 单一原件**：规范正文只在 `global/rules.md` 维护；全局指令与项目 AGENTS.md **只放指向本文件的短指针**，禁止复制条款正文，避免多处不同步。规范升版只改本文件并追加变更记录，注入端无需改动。
  > **受控例外（v2.0，见 〇⑦ ⑤）**：T1 是唯一允许不打开本文件的档位，平台全局指令因此可自带 〇⑦ ③ 最小红线集的 5 条**摘要**；这是唯一允许出现在注入端的条款内容，须与 〇⑦ ③ 逐条一致。改动 ③ 时维护者必须同步 `env/execution-enforcement.md` 二-L1 全文并通知人类重新粘贴，否则视为注入端过期。除此之外注入端仍只放指针。
- **⑥ 执行纪律与凭证（v1.8.9 新增，方案见 `env/execution-enforcement.md`）**：注入只是软约束，不能保证执行，故设三层递进机制：
  1. **开工自检简报（T2 强制，v2.0 收窄）**：**T2 会话**在写文件、改配置、装依赖、Git 写操作之前，**第一个输出必须是自检简报**——规范版本号、第八节全部 `[Agent自动]` 步骤结果、`tools-scan.sh --check` 结果、任务认领状态（含当前账号标识，见 三-8）、**当前挂起项**（读最新 handoff「挂起任务」快照，按项目 + 任务ID 分项目报出，见 三-4）、代理与双远端状态。未出简报即动手视为违规；简报后即可继续，无需人类确认。**T0/T1 的第一个输出改为「档位声明」**（本次档位 + 判定依据，见 〇⑦ ②），不出 10 步简报；档位判定错误或该 T2 却降级，按 〇④ 注入失败追查。
  2. **自检凭证与抽查**：平台 `SessionStart` 钩子（启用时）把自检结果注入上下文，并写 `~/.agent-tools/run/self-check/<session_id>.json`（时间戳、规范版本、自检结果；本机文件，**不入 Git**）；人类或审核方可随时抽查，缺凭证即按 〇④ 追查注入失败。
  3. **命令级硬门禁（可选，启用/停用由人类决定）**：平台 `PreToolUse` 钩子可在安装／部署类命令执行前 `deny`——缺自检凭证、命中全局安装（三-5 ②）、非授权 agent 部署（三-7）即拦截。钩子属平台 Beta 能力，**只覆盖本平台会话**，不覆盖其他 IDE/CLI；启用前必须先探针实测、先只记录不拦截、再打开拦截；脚本一律默认放行、超时 10 秒内、不联网、不写密钥。设计与启用顺序见 `env/execution-enforcement.md`。
  > 未启用钩子时，① 简报与 ② 凭证抽查仍为硬性要求（**T2 会话**）；不得因「钩子没开」跳过自检。

- **⑦ 会话分级加载与最小红线集（v2.0 新增，重大变更）**
  > **背景**：v1.8.x 要求「任何会话」首个输出都是 10 步自检简报、读 handoff / org.md / 挂起快照，对纯问答与本机单会话任务造成无谓负担与上下文污染；但 2026-11-05（全局装 wrangler）／11-08（用户级装 requests）两次事故证明「是否按规范」不能变成可选项。故改为**按档位分级加载**：减负，但不给破例口。

  **① 三档定义与判据（判定方向默认从严，拿不准按 T2）**

  | 档 | 客观判据 | 加载与自检 |
  |---|---|---|
  | **T0** 纯对话／只读 | 不写任何文件、不装依赖、不碰 `~/.agent-shared` / `~/.agent-tools` | 不读规范全文、不出简报；仅保留「涉及写操作前先读规范」 |
  | **T1** 本机单会话 | 只写当前工作区／项目本地文件，**同时满足 5 个否定条件**：① 不写 `~/.agent-shared`；② 不写 `~/.agent-tools`；③ 不装／升级任何依赖；④ 不认领任务卡；⑤ 不部署、不推双远端 | 不读 handoff / org.md / 挂起快照，不跑八节 10 步自检与代理核对；只遵守 ③ 最小红线集 |
  | **T2** 协作（**默认**） | 命中以下任一项即 **T2 且不得降级**：涉及 `~/source/` 下项目、写 `~/.agent-shared` 或 `~/.agent-tools`、安装／升级依赖、认领任务卡、部署、`git sync`、人类显式要求「开工前按规范自检」 | 全量执行八节 10 步自检 + 〇⑥ 简报 + 三-1 加载策略 + 五-1 推送前代理核对 |

  **② 声明与凭证**：T0／T1 的**第一个输出**必须声明档位与理由（如「本会话 T1：仅写当前工作区文件，不碰共享仓」），无需人类确认；T2 按 〇⑥ 出自检简报。平台 `SessionStart` 钩子启用时，凭证 `~/.agent-tools/run/self-check/<session_id>.json` 须记录档位与判定依据，供抽查（〇⑥ ②）。档位判定错误、或该 T2 却降级，按 〇④ 注入失败追查。会话中途转为写共享仓／安装／部署／认领任务卡／`git sync` 时，**立即升为 T2 并补做自检**。

  **③ 最小红线集（任何档位不可豁免，5 条；「不做什么」型禁令，零加载成本）**
  1. 密钥永不入 Git（六）；
  2. 禁把依赖装进全局或用户级位置，**按安装位置判定、不按命令写法**（三-5 ② / 四-5 ④）；**一旦需要安装／升级依赖即转 T2**，按四-4 ① 先探测、再决定是否安装；项目级 CLI 用 devDependency + lock + npx，通用库装 `~/.agent-tools/venvs/<agent名>/`；
  3. 不并行修改人类正在配置的目录／工具／服务；云同步目录内的删除交人类 UI（三-5 ⑥）；
  4. 不改 `global/rules.md` 正文，规范变更须人类批准（第十节）；
  5. 不碰他人未提交改动、不代提交、不强 rebase（三-5 ⑥⑦）。

  **④ 边界**：分级**只减加载量、不减共享仓写入纪律**——一旦写 `~/.agent-shared`，即已转为 T2，append-only、commit 格式、双远端、gitleaks、工具登记一条不少；平台全局指令只覆盖本平台会话，trae 等其他 IDE 仍走项目 `AGENTS.md` + 共享记忆，且写共享仓时同样按 T2；L3 命令级硬门禁未启用前，分级仍属软约束（〇⑥ ③）。

  **⑤ 注入端同步责任（〇⑤ 受控例外）**：T1 是唯一允许不打开 `rules.md` 的档位，故平台全局指令可自带上述 5 条**摘要**；这是 〇⑤「禁止复制条款正文」的唯一例外，摘要须与本节 ③ 逐条一致，**规范升版改动 ③ 时维护者必须同步更新 `env/execution-enforcement.md` 二-L1 全文并通知人类重新粘贴**，否则按注入端过期处理。

## 一、 架构总览与核心原则

- **单一事实源 (SSOT)**：核心资产（规范/记忆/技能/环境清单）托管于 Gitee 私有仓库（**主库**），GitHub 私有仓库作为**备份库**（见 五-1）。本地工作区对应 `~/.agent-shared`。
- **跨设备只同步文本资产**：规范、记忆、技能源码、环境清单、各类登记表。**跨设备不组网、不暴露远程服务**；移动端（iOS/HarmonyOS 无终端设备）为只读消费者，边界与例外见 四-3。
- **存储分层**：本地热数据（Git，文本资产） + 文档实时同步区（`~/.agent-docs`，第三方工具） + NAS 温数据（大文件） + 百度网盘冷数据（定时备份）。
- **物理隔离**：文本配置与状态（存于 `~/.agent-shared`）与 运行环境与工具（存于 `~/.agent-tools`）彻底分离。
- **本机资产不出本机**：运行时、venv、MCP 进程、临时文件、密钥，均属于本机，任何情况下不进入 Git 仓库。

## 二、 统一目录结构基准

在任何设备上，严格遵循以下两大核心目录的划分。

### 0. 路径映射基准 (v1.3 新增)
本规范所有 `~/` 写法在各系统的实际解析如下，脚本与文档中**禁止写死绝对路径**：

| 逻辑路径 | Linux / Termux | Windows (Git Bash 视角) | Windows (原生) |
|---|---|---|---|
| `~/` | `$HOME`（`/home/<user>`） | `~` → `/c/Users/<user>` | `C:\Users\<user>\` |
| `~/.agent-shared` | `/home/<user>/.agent-shared` | `/c/Users/<user>/.agent-shared` | `C:\Users\<user>\.agent-shared` |
| `~/.agent-tools` | `/home/<user>/.agent-tools` | `/c/Users/<user>/.agent-tools` | `C:\Users\<user>\.agent-tools` |
| NAS 挂载点 | `/mnt/nas` | `/z`（映射盘符 `Z:\`） | `Z:\` |

- Windows 上 `~` 由 Git Bash 解析为 `C:\Users\<user>\`，与规范约定一致；PowerShell 中等价写法为 `$HOME`。
- 移动端（iOS 等）不落本地工作区，只读边界见 四-3。

### 0.5 设备命名规范 (v1.3 新增)
- 格式：`<hostname>-<os>`，**全小写**，去掉空格与非 ASCII 字符；`os` 取枚举值：`win` / `linux` / `termux` / `harmony` / `ios`。全局唯一，冲突时在 hostname 后追加序号。
- 示例：`desktop01-win`、`nuc-linux`、`mate40-harmony`。
- 该名用于三处：`memory/devices/<设备名>.md`、handoff 文件名后缀（三-4）、记忆署名中的 `@设备`（三-1）。
- **设备总登记表** `memory/devices/_devices.md`，每行：`设备名 | os | 是否主设备 | nas 挂载能力 | 备注`。新设备接入时先登记，后使用。

### 1. 共享工作区目录 (~/.agent-shared)
在所有具备终端能力（Windows/Linux/Android-Termux）的设备上，统一使用 `~/.agent-shared` 作为本地工作区根目录（推荐直接 git clone 仓库至此）。
**只存放文本、代码、配置和记忆，严禁存放大型二进制包和依赖环境**。

```
~/.agent-shared/
├── global/
│   └── rules.md            # 本规范文件
├── memory/                 # 【读/写】长期记忆，全部 append-only
│   ├── org.md              # 组织级记忆（只追加，禁止改写历史行）
│   ├── projects/           # 各项目独立记忆文件

│   │   └── _devices.md    # 设备总登记表（见 二-0.5）
│   └── archive/            # 压缩归档（按 月/主题 命名，如 2026-10.md）
├── skills/                 # 【读】共享技能源码（按 coding / official-doc 分类）
├── handoff/                # 【读/写】任务交接（命名：YYYY-MM-DD-任务名-设备名.md）

│   ├── agents.md           # Agent 名登记表 + 账号登记表（见 三-1 / 三-8）
│   ├── repos.md            # 项目代码登记表 + 项目属性补充表（见 七，v1.8.11）
│   ├── toolchain.md        # 工具链基线与工具变更日志（见 四-4，v1.8.3 新增）
│   ├── tools-scan.sh       # 本机工具扫描脚本：--write 生成设备清单 / --check 核对基线（见 四-4）
│   ├── new-agent-bootstrap.md   # 新 Agent 一次性开场提示词（见 〇①，v1.8.9 补登）
│   ├── proxy-check.sh      # 代理与双远端只读核对（见 五-1 / 八-10，v1.8.9 补登）
```

### 2. 本机工具与依赖目录 (~/.agent-tools)
这是当前机器的**物理执行环境根目录**，不参与 Git 同步。所有 Agent 共享此目录下的运行时和工具，但依赖库互相隔离。

```
~/.agent-tools/                 # 本机所有 Agent 共享的工具根目录
├── bin/                        # 共享的可执行文件（加入系统 PATH）
├── venvs/                      # Python 虚拟环境隔离区
│   ├── workbuddy/              # 给 workbuddy 用的 venv
│   ├── codex/                  # 给 codex 用的 venv
│   └── dsh/                    # 给 dsh 用的 venv
├── node/                       # 共享的 Node.js 运行时（可选，或者用系统级）
├── mcp/                        # 本机安装的 MCP（含手动安装的定制 MCP）
├── cache/                      # 包管理器缓存（避免重复下载）
│   ├── pip/
│   └── npm/
└── run/                        # MCP 服务的 PID 文件和运行日志
    ├── fs.pid
    └── fs.log
```

### 3. 重要文档同步区 (~/.agent-docs) (v1.4 新增)
- **定位**：存放需要跨设备访问的**重要文档、资料库原件**（Office 文档、PDF、图表、设计源文件等）。**不进 Git**，由第三方同步工具（坚果云 / Syncthing / OneDrive）处理，确保多设备间文档实时一致。
- **与其他层的分工**：
  - 小而重要、需要跨设备**频繁查看/编辑**的文档原件 → `~/.agent-docs`（建议单文件 ≤ 100MB，避免触发同步工具的大文件/配额限制）；
  - 超大文件、视频、一次性归档、扫描件 → NAS `docs/`（见 五-2），不要求实时性；
  - 纯文本资产（规范/记忆/技能/清单） → Git 仓库 `~/.agent-shared`，不重复放一份进 `~/.agent-docs`；
  - **单一原件原则**：同一份文档只允许存在一个权威副本。严禁在 `~/.agent-docs` 与 NAS 各维护一份"双活"版本；确需留档时用脚本单向复制，并在副本文件头注明原件位置与复制时间。
- **路径约定**：所有设备统一使用 `~/.agent-docs`（Windows 为 `C:\Users\<user>\.agent-docs`）。若所选同步工具不支持自定义本地目录，则在本机建立符号链接（Windows `mklink /D`、Linux `ln -s`）指向实际同步目录，并将**实际路径**登记进 `memory/devices/<设备名>.md`。
- **工具约定**：全部接入设备必须使用**同一个**同步工具，由人类选定后在设备登记表 `_devices.md` 中记录。参考：坚果云——全平台（含 iOS/HarmonyOS）、国内直连，与本规范的多端组合最匹配；Syncthing——点对点无云中转、隐私性好，但 iOS 支持弱，适合纯桌面/安卓组合。选用云托管工具（坚果云/OneDrive）时，其账号凭证按 六（密钥管理）手动分发并加入 `keys-checklist.md`。
- **引用约定**：handoff 与记忆中引用文档统一写 `docs://<相对 ~/.agent-docs 的路径>`，如 `docs://产品/需求说明书-v2.docx`，解析方式与 `nas://` 相同（查本机设备登记的映射）。**该约定同样是文本约定，不依赖任何驱动**。
- **目录结构建议**（不强制）：按项目/类别建一级目录，如 `docs/产品/`、`docs/资料库/`、`docs/财务/`。
- **移动端**：`~/.agent-docs` 是无终端设备（iOS 等）唯一能直接读写二进制文档的通道（经同步工具的 App），agent 在为移动端准备材料时应优先放此处而非 NAS。

## 三、 核心工作规范

### 1. 记忆管理 (Memory)
- **上下文加载策略（v1.5 新增，控制 token 消耗；v2.0 起按 〇⑦ 档位执行）**：
  - **档位门槛（v2.0）**：T0 不加载任何共享仓上下文；T1 不加载 handoff / org.md / 挂起快照 / 项目记忆任务登记节；T2 才按下列策略全量加载。
  - `org.md` 默认**只读取最近 200 行**（`tail -200`），不全文加载；
  - `memory/archive/` **不默认加载**，仅按需 grep 检索特定主题；
  - 项目记忆只加载当前项目的对应文件，不加载其他项目；
  - handoff 默认只读取最新一份交接文档，不扫描全目录；**多项目例外（v1.8.11）**：本会话涉及两个及以上项目时，按项目各读最近一份带该项目标签的 handoff（凭文件头 `项目:` 行或任务名前缀定位，**只多读该文件、不全文加载**），避免高频项目的交接流把低频项目上下文挤出窗口；
  - `org.md` 是跨项目混流的组织级记忆，最近 200 行窗口不保证包含任一特定项目的条目；**项目事实以 `memory/projects/<项目名>.md` 与该项目 handoff 为准**，不得因 org.md 未出现就判定项目无记录。
- **Agent 名登记**：agent 名必须在 `env/agents.md` 登记（格式：`agent名 | 所属设备 | 职责`），未登记的 agent 名在署名中**视为无效**；同名 agent 登记在不同设备视为不同实例，署名时以 `agent名@设备名` 区分。同一设备同名 agent 的**多个并发会话**视为同一实例的不同会话（见 三-5 ⑦）：需要区分归属时署名可追加会话标识 `[@agent名 @设备名#s1 YYYY-MM-DD HH:mm UTC+8] 内容`，禁止两会话混用同一署名导致无法定责。**多账号定责（v2.1，见 三-8）**：同一 agent 名在同一设备下有多个平台账号时，署名可再加 `~<账号标识>`，即 `[@agent名 @设备名~<账号标识>#<会话标识> YYYY-MM-DD HH:mm UTC+8] 内容`；防撞键仍为「项目 + 任务ID」。
- **append-only 原则**：所有记忆文件只允许在文件末尾追加，**禁止修改、删除或重排已有行**。修正错误信息时追加一条更正记录，不改原文。**唯一例外见 三-2 记忆压缩**。
- **署名规范**：每条追加必须带前缀，格式为：
  `[@agent名 @设备名 YYYY-MM-DD HH:mm UTC+8] 内容`
  无署名或 agent 未登记的记忆条目视为无效，可被压缩时剔除。
- 本机特有信息（路径、端口）只能写在 `memory/devices/本机名.md` 中。
- **冲突避免**：append-only + 各设备写各自文件（handoff 按设备命名）使 Git 冲突几乎不会发生。若仍遇冲突：先 `git pull --rebase`，保留双方行、按时间重排，然后 **push 前执行 `git log --oneline -5` 目视确认历史完整（防止自动解决弄丢压缩提交等关键 commit）**，再 push；无法判断时标记 `<!-- 待人工裁决 -->` 并通知人类。

### 2. 记忆压缩机制 (Compaction)
- **append-only 的唯一例外**：记忆压缩是**唯一允许改写记忆文件（截断/重组）的机制**，且仅限主设备在压缩窗口内执行。窗口外任何改写记忆文件的行为均违规。
- **周期**：每月 1 次（人类用户发起，建议固定在每月第一个周末）。**保留期统一为 90 天**（记忆条目与交接文档一致），压缩流程中**一步同时处理 `memory/` 与 `handoff/` 的归档**，避免两套周期漏处理。
- **执行者**：由人类指定的一台**主设备**（建议：主力 Windows 机）上的任一 agent 执行，同一周期内只允许这一台设备执行压缩。
- **锁文件机制（v1.5 变更）**：压缩前先创建 `memory/.compact-lock`（内容：设备名 + ISO 时间戳）并**单独 commit + push**。其他设备自检时发现锁即**暂停写入记忆**，直至锁被删除。压缩完成后，删锁与压缩内容在同一个 commit 中一并推送。
- **流程**（严格按序）：
  1. `git pull --rebase` 确保最新；
  2. 创建并推送 `memory/.compact-lock`（含设备名+时间戳），从 push 锁起进入压缩窗口，**全流程原则上不超过 30 分钟**；
  3. 读取 `org.md` 及各项目记忆全量内容；
  4. 将超过 90 天的条目提炼为摘要，写入 `memory/archive/YYYY-MM.md`（按主题分节，保留决策结论与关键链接，丢弃过程细节）；同时将超过 90 天的 handoff 移入 `handoff/archive/YYYY-MM/`；**挂起项归档保护（v1.8.10）**：压缩前对照最新 handoff 的「挂起任务」快照，把仍未解挂且超过 90 天的项逐条写入当月归档摘要（项目 / 任务ID / 挂起原因 / 解挂前置 / 裁决出处），并在压缩后生成的最新一份 handoff 中续记，禁止随旧 handoff 进入只读归档而丢失；
  5. 将 `org.md` 截断为：压缩后的最新摘要 + 保留期内原始条目；同 commit 删除 `.compact-lock`；
  6. 立即 push，commit message 格式：`memory: compact 2026-11 by <agent>@<设备>`；
  7. **验证备份库**：push 后在临时目录对 GitHub backup 远端执行一次 `git clone --depth 1`，确认镜像可用；
  8. **维护各项目 worktree**：对本机 `~/source/` 下各项目执行 `git worktree prune`，并清理已合并的 `agent/*` 本地分支（见 三-6）。
- **归档只读**：`memory/archive/` 与 `handoff/archive/` 下的文件**一经写入即为只读**，后续周期不得修改既有归档，新月份/新周期新建文件。

### 3. 临时文件与跨设备文件分类
- **严禁**在工作区根目录或 `handoff/` 下生成临时文件，所有中间产物必须写入 `tmp/<agent名>/`（**按 agent 子目录隔离**，防止多 agent 互踩）；同一 agent 存在多个并发会话时，各会话再细分 `tmp/<agent名>/<会话标识>/`（见 三-5 ⑦）；会话结束时主动清理；各设备可配置定时任务清理 7 天以上的残留文件。
- **跨设备文件分类标准（v1.5 新增，客观可执行）**：

  | 文件类型 | 去向 |
  |---|---|
  | ≤1MB 的文本/代码/配置 | 直接 commit 到对应目录 |
  | 重要文档（Office/PDF/图表，≤100MB） | `~/.agent-docs`，引用写 `docs://` |
  | >100MB、二进制、视频、归档 | NAS `docs/`，引用写 `nas://` |
  | 无法归类的中间产物 | 默认 `tmp/`（本机），并在交接文档中说明去向 |

- 判定困难时**宁可用 tmp/ 也不要污染 Git 仓库**；一旦发现中间产物被误提交，应在同一会话内 `git rm` 并在下一次压缩时清理。

### 4. 任务交接 (Handoff)
- 完成阶段性任务、切换设备或结束会话时，**必须**在 `handoff/` 下生成交接文档，命名：`YYYY-MM-DD-任务名-设备名.md`（带设备名，避免多端同名冲突）；同机同日多会话任务名相同时，文件名追加会话标识或时分秒后缀，**禁止同名覆盖**（见 三-5 ⑦）。
- 交接文档需包含：当前状态、已完成、待办、关键文件链接（见五-2 引用规范）、当前使用的 worktree 路径与分支（如适用，见 三-6）、下一步指令。
- **项目标签（v1.8.11）**：文件头必须写 `项目: <项目名>` 元数据行（跨项目写多个逗号分隔；规范／环境／工具等全局任务写 `项目: 全局`），任务名建议带项目名前缀。**不改命名格式** `YYYY-MM-DD-任务名-设备名.md`，历史文件不追溯补写；新会话凭此标签按项目检索最近一份 handoff（三-1 多项目例外）。
- **归档**：超过 90 天的交接文档，随月度记忆压缩一并移动至 `handoff/archive/YYYY-MM/`。

#### 挂起任务登记（v1.8.10 新增）

> **定义**：挂起（`suspended`）＝任务因外部条件或人类裁决未完成而**暂时禁止开工**；不算完成、不算放弃、不释放任务所有权。与「待办」（可认领）、项目 `BOARD.md` 的「阻塞项」（业务记录）区分开。字段模板见 `env/handoff-suspended-template.md`。

- **① 双落点，不新建第二事实源**：
  - **事件流（管定责）**：`memory/projects/<项目名>.md` 任务登记节 append-only 追加 `【挂起】<任务ID> | <时间> | <原因> | <裁决出处>` 与 `【解挂】<任务ID> | <时间> | <前置满足的证据>` 行；格式沿用 三-5 ⑤，状态值写 `suspended`，禁止改写旧行。
  - **当前快照（管防撞）**：**最新一份 handoff** 固定设 `## 挂起任务（当前全量快照）` 小节，列出**当前所有未解挂项**，而非仅本次新增项。每写一份新 handoff 都要继承未解挂项（滚动继承）；解挂项在新 handoff 中标注「已解挂 → 待办／重新认领」，**禁止改写旧 handoff**。
- **② 快照必填字段（v1.8.11 共 8 项）**：`项目 | 任务ID | 挂起于/裁决出处 | 原因 | 解挂前置（可验证条件） | 现场 | 解挂后动作 | 解挂权`；首列 `项目` 必填，**防撞按「项目 + 任务ID」匹配**——禁止把 A 项目的挂起项当作 B 项目的开工禁区或反之，也避免不同项目复用 `T-0xx` 编号时撞车。解挂前置必须是**可判定条件**（如「产出某文件 + 人类裁定 #N」），禁止写「等通知」；现场三选一写明：① 保留 worktree + 分支（登记路径与基座，其他会话禁用）／② **remove worktree、成果留在分支（默认，符合 三-6）**／③ 全部清理仅留 `tmp/` 与文档；凭据一律经环境变量、不落盘。
- **③ 状态机与权限**：`todo → doing → suspended`；解挂后按现场是否保留回 `todo`（重新认领）或 `doing`（续跑）。**挂起与解挂权归人类**（第十节）；agent 发现应挂起时只上报并写「建议挂起」，不得自行挂起／解挂，也不得把挂起卡当 `todo` 开工。一次性豁免（如「允许并行」）须写明授权范围、不得扩大解释、先留痕后派工。
- **④ 防撞与自检**：三-5 ⑤⑦ 的「不得开工」判定集合含 `suspended`；〇⑥ 自检简报须按项目报「当前挂起项」，匹配键为「项目 + 任务ID」。项目 `tasks.md` 卡面状态**保持 `todo` 不变**，不改状态枚举（`check.mjs` 门禁锁死 `todo/doing/blocked/done`），挂起约束由共享层快照提供。
- **⑤ 归档保护**：按 三-2 第 4 步，跨 90 天仍未解挂的项写入当月归档摘要并在最新 handoff 续记，不得随旧 handoff 归档而消失。

### 5. 多 Agent 并发纪律 (v1.5 新增，v1.6 扩充)
- **同机并发前提**：同机多个 Agent **可以同时运行**，但必须同时满足以下四条：
  1. **各用各的 venv**：依赖隔离遵循 四-1，装入并激活 `~/.agent-tools/venvs/<自己的名字>/`，禁止共用或激活他人虚拟环境；
  2. **禁止全局安装**（v1.8.4 明确化）：不得执行 `npm install -g` / 系统级 `pip install` / `pip install --user` 等把包装进**共享前缀**的命令。"全局"按安装位置判定，**不按是否需要管理员权限判定**——装进 `~/.workbuddy/binaries/node/versions/*`、`%APPDATA%\npm` 等用户级托管目录同样算全局安装，一律禁止（Windows 上"以管理员身份"安装更在其内）。**判定看包最终落在哪里，不看命令写法**：`pip install`（不带 `--user`）在托管 Python 上默认落入用户级 `%APPDATA%\Python\...\site-packages`，同样算全局安装（2026-11-08 requests 2.34.2 事故，v1.8.9 明确）。缺依赖时：Python 装进自己的 venv；**Node/项目级 CLI 必须声明为项目的 devDependency 并装在项目的 `node_modules/` 内**，用 `npx <tool>` 或 npm scripts 调用（见 四-4 ⑦）。唯一例外是基础运行时本身（Git/Python/Node，四-1 允许系统装一份）。通用只读解析库（pypdf 等）的归属、登记与跨会话复用见 **四-5**；**禁止以「让所有会话共用」为由把库放进全局/共享前缀**。
  3. **项目目录占用确认（兜底）**：对项目目录的并行操作**默认走 三-6 worktree 模式**（各用各的 checkout，无需占用确认）；仅当共用主 worktree（临时小改动）时，先查 `handoff/` 最新交接文档确认无其他 Agent 占用，开始占用时**必须在交接文档中注明占用者与预计释放时间**，禁止并行操作同一目录；
  4. **命名隔离与端口段**：临时文件一律写入 `tmp/<agent名>/`；Agent 因调试等需要自起的服务必须带 agent 名命名与登记（端口记录进 `memory/devices/<设备名>.md`），**禁止占用 9101/9102 等本规范保留端口**，避免服务与文件被静默互相覆盖。dev server、测试数据库、docker 容器等开发资源按 **agent 端口段**分配（如 trae=9200-9299、workbuddy=9300-9399），端口段登记进设备档案，禁止越段占用。
  5. **任务认领机制**：项目开发任务统一登记在 `memory/projects/<项目名>.md` 的任务登记节（append-only），格式：`任务ID | 描述 | 认领agent | 状态`。agent 领任务先追加认发行（登记即锁定），完成或放弃必须**追加**状态行（不得改写旧行）；未登记认领的任务其他 agent 不得开工，防止重复劳动。**防撞集合（v1.8.10）**：开工前除查 `doing/open` 外，还须读最新 handoff 的「挂起任务」快照，状态 `suspended` 的任务一律不得开工（挂起不等于 `todo`），详见 三-4。
  6. **人类操作优先原则**：人类正在配置或操作的目录、工具、服务（含各类云同步客户端、NAS、网盘），agent **禁止并行修改**，动手前必须确认人类的配置进度与意图；云同步目录内的删除操作一律由人类在客户端/网页 UI 完成，agent 不做本地侧反复删除重试（源自 2026-11-04 agent-docs 配置冲突事故复盘）。
  7. **同 agent 多会话并发（v1.8.6）**：本节全部纪律同样适用于**同一 agent 名的多个并发会话**（不同平台/不同窗口的会话），不因「同一个 agent」而豁免。要点：① **任务认领是跨会话防撞的第一道闸**——开工前必查 `memory/projects/<项目名>.md` 登记节与最新 handoff 的挂起快照，任何任务已被认领（状态 doing/open）或处于挂起（suspended）即不得开工，**无论认领者是否自己**；② 临时目录与 worktree 按会话/任务细分：`tmp/<agent名>/<会话标识>/`，worktree 并发时用 `~/source/<项目名>.wt/<agent名>-<任务>/`（或序号后缀），串行复用同一 worktree 目录须先确认对方会话已结束且工作区干净；③ 自起服务在 agent 端口段内按会话登记实际占用端口（记入设备档案），先查后占；④ 记忆与交接署名按 三-1 可追加 `#<会话标识>` 以便定责。**多账号特例（v2.1）**：同一 agent 名的多个平台账号按本条同等处理，目录／worktree／端口细分用 `<账号标识>`，`venvs/<agent名>/` 仍共用一份；凭据共用边界按 三-8 ⑥⑦（**同一台设备 + 同一个 agent 软件可共用，跨设备／跨 agent 软件禁止**）；详见 三-8。
- **传输层**：同机 agent 共享同一 MCP SSE 服务（四-2），请求由服务进程排队，**禁止**为并发而自起 stdio 实例。
- **Git 操作串行化**：同机多个 agent 执行 `pull/commit/push` 等写操作时，必须先获取本机文件锁（Linux/Git Bash 用 `flock`，Windows 用 PowerShell `Mutex` 或等价锁文件 `~/.agent-tools/run/git.lock`），**同一时刻同机只允许一个 git 写操作**；锁等待超过 60 秒即报告人类而非无限等待。
- **文件写入隔离**：记忆 append-only、handoff/`tmp/` 按设备与 agent 命名，已从命名上消除绝大多数并发写冲突。两 agent 确需写同一文件时，以 Git 提交先后为准，**禁止长时间持有未提交的编辑**（编辑后 10 分钟内必须 commit 或放弃）。
- **项目代码并发**：多 agent 同时修改同一项目代码时，走 三-6 worktree + `agent/*` 分支协作，由人类合并。

### 6. Git Worktree 协作 (v1.7 新增)
- **适用场景**（v1.8.2）：**单人单任务直接 clone 到 `repos.md` 登记路径，不启用 worktree**——worktree 的唯一目的是隔离同机多 agent 对同一项目的并发修改，无并发时启用它只增加清理负担。仅当两个及以上 agent 同时修改同一项目代码时，才按下述布局启用协作模式。
- **范围**：仅 `repos.md` 登记的项目代码仓库；**`~/.agent-shared` 禁用 worktree**（append-only 记忆与压缩机制依赖单一历史，分支化会使其失效）。
- **布局**：主 worktree `~/source/<项目名>`（跟踪 main，人类或共用者使用）；agent 专属 `~/source/<项目名>.wt/<agent名>/`，分支 `agent/<agent名>/<任务>`；同 agent 并发多会话/多任务时 worktree 目录扩展为 `<agent名>-<任务>`（见 三-5 ⑦）。
- **流程**：领任务后（先按 三-5 ⑤ 认领登记）`git worktree add ~/source/<项目名>.wt/<agent名> -b agent/<agent名>/<任务> origin/main` → 开发/构建/测试 → **分支准出**：`git pull --rebase origin main` 且自测（至少构建+冒烟）通过，commit 携带 `Agent: <agent名>` trailer，并以独立提交身份提交（`git -c user.name=zhn-<agent名> -c user.email=<agent邮箱> commit ...`）——**禁止用裸 `git config user.name/user.email`**：worktree 默认与主仓库共用 `.git/config`，会篡改主 worktree 的署名（v1.8.5 勘误，见 〇 相关公告）→ push 分支 → 人类合并 → `git worktree remove`。
- **生命周期**：会话结束即 remove，成果靠分支保留而非残留目录；月度压缩时主设备顺带 prune 并清理已合并的 `agent/*` 本地分支（三-2 第 8 步）。**挂起例外（v1.8.10）**：任务挂起时默认 remove worktree、成果留在分支，并在 handoff 挂起快照「现场」栏登记分支名与基座；确需保留 worktree 须写明路径并禁止其他会话复用（三-4 ②）。
- **依赖**：Python venv 位于 `~/.agent-tools/venvs/`，跨 worktree 直接复用；`node_modules` 每 worktree 独立安装，依赖共享缓存 `~/.agent-tools/cache` 降低代价（pnpm 项目 store 天然共享）。

### 7. 部署权限与审核后处置（v1.8.8 新增）

> 「部署」含 `wrangler deploy`、云平台发布、数据库迁移执行、服务重启等一切使**线上行为发生变化**的动作；不含本地构建与 `git push`（push 不等于部署，2026-11-06 已实测确认）。

- **① 权限默认收口**：默认只有**审核方 workbuddy** 具备部署判断权。**其他 agent 一律不得操作部署**（含完成编码的 trae），只有人类在**当次任务里明确点名授权该 agent** 时才例外；授权不可跨任务、跨会话、**跨账号**推定，也不因「该 agent 写了这段代码」而自动获得；人类点名授权时须写明针对哪个账号（三-8）。
- **② 审核通过后的处置**：任务复审通过 → 合并收官 → workbuddy **自行判断**是否直接部署。**能确定就直接部署，不必逐次询问人类**；**不能确定就通知人类部署**，并说明卡在哪一项、给出可复制的部署命令与部署后自检项。禁止猜测、试部署，或把「大概率没问题」当作确定。
- **③ 「能确定」必须同时满足**（缺一即通知人类）：
  1. 改动范围已在卡面／审核记录中列全，且仅限**已合并的代码与生成物**；不涉及 D1 migration、表结构变更、secret／环境变量／账号／域名／路由／绑定／计费配置变更；
  2. 部署命令来自项目 `package.json` scripts 或项目记忆里已登记的入口（**项目级 CLI 用项目本地 `node_modules`，见 四-4 ⑦**），本机可用且无需交互式登录；凭据有效或已确认可免登录；
  3. 部署目标明确（哪个服务／环境），且**人类当前没有正在操作该服务**（三-5 ⑥ 人类操作优先）；
  4. 部署后有可执行的线上自检（资源 md5／HTTP 状态／关键特征），失败能判定并给回滚建议。
- **④ 必须通知人类的情形**（任一命中即停）：涉及 migration／secret／配置／凭据／域名变更；部署命令或登录态不可验证；首次或路径不明确的部署；生产事故期间的恢复动作需人类拍板；网络异常（如 Cloudflare 链路超时）；其他 agent 请求部署；人类正在配置或操作同一服务。
- **⑤ 部署后**：立即线上自检，并在 `memory/projects/<项目名>.md` 与当日工作日志留痕（部署时间、基线提交号、部署者及其账号标识、自检结果）；自检不通过**立即报告人类并给回滚建议，禁止反复重试**；不得替其他 agent 或人类「顺手再发一版」。
- **⑥ 状态同步**：共享记忆须写明当前线上版本与基线是否一致（历史上出现过「代码已合并但线上仍是旧版、人类以为已修复」的白屏延续事故，见 2026-11-06 prnmgt T-053 记录）；判断由人类部署时须明确写「待人类部署」，避免其他会话误判生产已恢复。

### 8. 多账号协同（v2.1 新增，v2.2 订正凭据边界与账号标识命名）

> **背景**：同一 agent 软件（如 WorkBuddy）可能在同一台设备上以多个平台账号登录；本机实测 `~/.workbuddy/user-28f31f12…-personal` 与 `user-a817c1b8…-g3ycua53lwqo` 两个账号目录并存。技能层「个人版／企业版共存」结论见 `skills/official-doc/zhn-docs-kb/SKILL.md` 15.8；本节只管**协同调度层**（署名、认领、注入、凭据、部署授权），不重复三层资产清单。

- **① 定位**：账号是**定责标签 + 凭据／权限域**，**不是新的身份主键**，也不是防撞键。共享仓 `~/.agent-shared` 只有一个，**不按账号拆分**——拆开会破坏 〇⑤ 单一原件、三-1「只读最新一份 handoff」与三-2 的 90 天归档；`handoff/`、`org.md`、`tmp/` 同样不按账号分目录。
- **② 账号标识由人类命名**：在 `env/agents.md` 的「账号登记表」登记，字段 `账号标识 | 平台/版本 | 主体 | 关联agent名 | 设备 | 注入状态 | 凭证边界 | 状态/启用日期`。**未登记的账号标识不得用于署名、认领、部署**；agent 不得自取、不得从目录名推断账号名。**已正式命名（人类 2026-11-12 11:49）**：`zhn-x`（个人版）、`zhn-3b`（企业／团队版）；旧暂用名 `personal` / `corp` 的映射见登记表，**历史条目不追溯改写**。
- **③ 定责键（可选后缀）**：记忆行 `[@agent名 @设备名~<账号标识>#<会话标识> YYYY-MM-DD HH:mm UTC+8 内容]`；commit `… by <agent名>@<设备名>~<账号标识>`；项目代码 `Agent:` trailer 不变。**历史条目不追溯改写**，无后缀一律视为该设备上的默认账号。
- **④ 防撞键不变**：任务认领与挂起防撞仍按「**项目 + 任务ID**」（三-4 / 三-5 ⑤）。账号**不进入防撞键**——否则同一张卡会被两个账号各认领一次。三-5 ⑤「无论认领者是否自己」跨账号同样成立：A 账号认领的卡，B 账号也不得开工；同为 `suspended` 的快照项对两个账号一律生效。
- **⑤ 注入按账号各配一次**：平台全局指令（〇① 1）须在每个账号下各配置一次，并各做一次 〇④ 首次注入验证；磁盘上 `~/.workbuddy/app/app-config.json` 只有一份机器级副本；**2026-11-12 已实测关闭该待验证项**——企业版账号登录后文件 mtime 更新但指令指纹未变，两个账号读同一份、注入均生效（见 `env/agents.md` ② 实测结论）。未注入账号的会话按 〇③ 停止写操作并上报人类。`user-<id>-*` 身份／记忆文件按账号隔离，**禁止跨账号复制**。
- **⑥ 并发资源细分与凭据共用边界（v2.2 订正）**：同 agent 名多账号按三-5 ⑦ 跨会话并发同等处理——`tmp/<agent名>/<账号标识>/<会话标识>/`、worktree `.wt/<agent名>-<账号标识>-<任务>/`、自起服务在 agent 端口段内按账号登记实际端口；`~/.agent-tools/venvs/<agent名>/` **默认仍共用一份**（四-5 ② 不按账号拆分，避免重复安装与版本漂移）。**凭据类（凭证、登录态、连接器授权）的共用范围限定为「同一台设备 + 同一个 agent 软件」**（人类 11:49／11:50 定义，即「同一 agent」的准确含义）：该范围内同一 agent 软件的多个平台账号**可共用**一份 `config/` 与机器级连接器授权，不单独分发；**跨设备、跨 agent 软件一律禁止**共用、复制或分发。身份／记忆目录仍按账号隔离（⑨）。`config/` 与 `venvs/` 是**设备级／agent 软件级**目录，同机已登记的多个 agent 名读取同一份物理文件属既有设备级用法，但不得据此把登录态或连接器授权搬到另一台设备或另一软件。
- **⑦ 凭据边界（v2.2 订正，原「主体边界」）**：`config/` 是**设备级**凭证（六），共用范围见 ⑥。
  - **允许**：同一台设备、同一个 agent 软件下的多个平台账号共用一份 `config/`、私钥／token 与机器级连接器授权；人类 2026-11-12 11:44 已裁决「企业账号不单独分发凭证」「接受连接器授权机器级共享」（个人授权对企业账号可见、反之亦然），不另做隔离。
  - **禁止**：把 `config/`、私钥／token、登录态或连接器授权**复制到另一台设备**或**搬给另一个 agent 软件**；新设备仍按 六节由人类手动逐项分发；把平台登录态写进共享仓。
  - **附加条件**：若同一设备同一 agent 软件下出现**不同主体**账号（个人／企业分属不同法人），是否仍共用须人类单独裁决，不得按「同设备」自动推定（判断方法见技能 15.8）。
  - `keys-checklist.md` 标注「适用设备 + agent 软件」；自检第 1 步（八-1）按当前设备核对适用项，不因另一账号缺项而误报。
- **⑧ 部署授权**：三-7 的授权**不可跨账号推定**——「人类当次点名授权」须写明针对哪个账号；部署留痕须含账号标识（三-7 ⑤）。
- **⑨ 禁止**：按账号拆共享仓或 handoff 目录；把账号写进防撞键；agent 自判账号；**跨设备／跨 agent 软件复制 `config/`、登录态或连接器授权**；**跨账号复制 `user-<id>-*` 身份／记忆目录**（身份层隔离不因 ⑥⑦ 放宽）；把账号级记忆写进 Git（最小红线集①）。
- **⑩ 与技能层分工**：技能 15.8 的三层资产表（技能＝机器级／身份记忆＝账号级／连接器凭证＝机器级）作为引用附件，本节不重复也不覆盖；两者冲突时以本节（协同规范）为准，技能文档按第十节上报人类订正。

## 四、 工具与 MCP 机制

### 1. 依赖与运行时安装纪律
- **系统级共享**：Python/Node.js/Git 等基础运行时系统安装一份即可。
- **环境隔离**：Agent 专属的 Python 依赖必须安装在 `~/.agent-tools/venvs/你的agent名字/` 中；**Node/项目级 CLI 依赖必须装在项目的 `node_modules/` 并由项目 lock 文件声明**（见 四-4 ⑦），不得装进共享全局前缀（三-5 ②）。venv 按 **agent 名** 隔离、不按会话隔离：同一 agent 名的多个会话共用同一份，通用库的放置与复用细则见 **四-5**。
- **禁止违规存放**：严禁在 `~/.agent-shared` (Git 工作区) 内部创建任何 `venv` 或 `node_modules`。
- **Windows Shell 选型（v1.3 新增）**：
  - **Git Bash 为主**：负责运行 `env/` 下全部 `.sh` 脚本（`setup.sh`、`start-mcp.sh` 等），保证与 Linux/Termux 单套脚本通用，且 `~` 解析与本规范一致；
  - **PowerShell 为辅**：仅用于 Windows 原生**计划任务**的注册与调度（MCP 开机自启、`tmp/` 7 天清理、夜间备份），以及在脚本中调用 `rclone.exe`；
  - **不使用 WSL**：WSL 会产生第二个独立的 `~`（位于 ext4 虚拟磁盘内），将工作区劈成两份、破坏"唯一工作区在 `C:\Users\<user>\`"的约定，明令禁用。

### 2. MCP 分级管理（v1.2 变更）
- **同机多 Agent 共享**：同机所有 Agent **必须连接同一个本地 MCP SSE 服务**，禁止各起 stdio 进程抢文件。服务只绑定 `127.0.0.1`，**不对外网/局域网暴露**。
  - 默认地址：`http://127.0.0.1:9101/sse` (文件系统，访问根目录限制为 `~/.agent-shared` 与 NAS 挂载点)
  - 默认地址：`http://127.0.0.1:9102/sse` (Git 操作)
- **公开市场 MCP**：统一配置在 `env/mcp-config.json`，随 Git 同步。各设备执行 `start-mcp.sh`（或对应 Windows 计划任务）时按配置自动拉起。
- **定制 MCP（手动安装）**：源码不参与同步。安装后**必须**在 `env/mcp-registry.md` 登记，每条包含：

  ```
  | 名称 | 用途 | 来源(仓库/下载地址) | 安装命令 | 版本 | 安装日期 | 已装设备 |
  ```

  换设备或重装系统时，依此登记表人工还原。**未登记的定制 MCP 视为不存在**。

### 3. 跨设备访问（v1.2 变更：不组网）
- **不使用** Tailscale / ZeroTier 等组网方案，**不提供**远程 MCP。
- 无终端设备（iOS/HarmonyOS 等）**默认只读**：通过 Git 托管平台的客户端 App（或网页）阅读 `memory/`、`handoff/`、`repos.md` 等文本资产，二进制文档经同步工具 App 访问 `~/.agent-docs`。
- **移动端写操作的唯一例外**：仅限在 `handoff/` 下紧急补录一份交接/备忘文件；该提交**必须**由人类在桌面端复核后合并（rebase 或接受 PR），桌面端 agent 发现移动端未复核提交时应提示人类。除此之外移动端不产生任何写入。

### 4. 工具链基线管理（v1.8.3 新增）

本机已有工具**优先复用，不得重复下载安装**。工具链分三层登记，不得混用：

| 类别 | 登记去处 |
|---|---|
| 系统级基线（git/python/node/npm/gh/curl/unzip/ssh）与工具区二进制（gitleaks 等，放 `~/.agent-tools/bin`） | `env/toolchain.md`（基线、来源类型、变更日志）+ `memory/devices/tools-<设备名>.md`（本机实测，脚本生成） |
| 项目/venv 依赖 | `env/requirements.txt`、项目 lock 文件 |
| **通用只读解析库**（pypdf 等，v1.8.7 新增，见 四-5） | `env/requirements.txt` 固定版本 + `env/toolchain.md` §五 变更日志（**装进 `~/.agent-tools/venvs/<agent名>/`**） |
| **项目级 CLI**（wrangler / vite / tsc / eslint 等，v1.8.4 新增） | **项目自身的 `package.json` + lock 文件**（devDependency，装进项目 `node_modules/`，见 ⑦） |
| MCP 服务 | `env/mcp-registry.md`（见 四-2） |
| 桌面客户端（WPS/PuTTY/网盘/NAS 映射） | `memory/devices/<设备名>.md`（属人类环境，不在工具链基线内） |

- **① 探测优先，缺失才装**：任何安装动作前先 `command -v <tool>` + `<tool> --version`；**已装且满足基线即直接用**，登记来源为 `复用`，禁止无谓重复安装（既省时间，也避免同机多版本互相干扰）。解析/转换类需求（PDF、图片、Office 等）还须**先探测平台内置 CLI**（如 `~/.workbuddy/external-packages/` 下的 pdf-cli），满足需求即直接调用、不装第三方库（见 四-5 ①）——平台能力优先于任何安装动作。
- **② 首次扫描一次，之后增量**：新设备或新 agent 首次运行时执行一次
  `bash env/tools-scan.sh --write`
  生成 `memory/devices/tools-<设备名>.md` 并刷新 stamp（`~/.agent-tools/run/tools-scan.stamp`），随后提交并 `git sync`。
  **已有 stamp 且未满 30 天时，其他 agent 不得再全量扫描**，只跑 `bash env/tools-scan.sh --check` 核对基线即可；超过 30 天才重新全量刷新（避免同一台机器被反复扫描、清单反复抖动）。
- **③ 新装 / 升级 / 卸载必须登记**：**系统级工具与工具区二进制**执行 `tools-scan.sh --write` 刷新本机清单，并在 `env/toolchain.md` §五 变更日志**追加一行**（日期 | 设备 | 操作 | 工具与版本 | 来源类型 | 操作者 | 备注）；**项目级 CLI** 则由项目 `package.json`/lock 文件的提交来登记（并在 `memory/projects/<项目名>.md` 追加一条说明）。**未登记的安装视为不合规**——无论装在系统级、用户级托管前缀还是项目外，都不能以"某会话临时装一下"为由跳过登记。
- **⑦ 项目级 CLI 归项目所有（v1.8.4 新增）**：wrangler、vite、tsc、eslint 等**只在某个项目里用得到**的命令行工具，必须声明为该项目的 devDependency，装进项目 `node_modules/`，随项目 Git 仓库（lock 文件）走，用 `npx <tool>` / npm scripts 调用。**禁止装成全局**——全局安装会造成：① 所有项目/会话共用同一版本，互相冲突；② 新设备 clone 项目后拿不到该命令，部署/构建不可复现；③ 无法从任何清单看出这台机器装过它。
  - 探测时还要查项目自身的 `package.json` / lock 文件，不能只看 `command -v`；仅当项目确无依赖声明且确实需要该工具时才安装，且必须按上述方式落到项目本地。
  - **存量整改**：发现历史上已全局安装的项目级 CLI，按"卸载全局 → 项目本地化 → 补登记（`toolchain.md` §五 追加卸载与安装各一行 + 项目记忆说明）"处理，禁止用"补一条登记"把违规状态合法化。
- **④ 来源类型必填其一**：`复用`（本机已装直接用，首选）/ `包管理器`（winget/apt/brew/scoop，记包名）/ `官方Release`（记版本号与下载 URL）/ `未知来源`（绿色版、他处拷贝——可直接用，但**密钥相关工具须核验哈希或换官方来源**）。
- **⑤ 约束**：工具二进制**不入 Git**，`~/.agent-tools/bin` 为唯一工具区，禁止散落到项目目录；不登记 `pip list`/`npm ls` 这类完整包列表（噪音），只登记 agent 干活真正依赖的工具；多版本并存时须在设备清单注明"默认解析哪个"，否则 agent 会用错解释器装包。
- **⑥ GUI 程序（puttygen 等）不做版本探测**：执行 `--version` 会弹窗挂起会话，清单里记为"未探测"即可，只核对存在性。

### 5. 通用依赖库的分层放置与复用（v1.8.7 新增）

**结论：统一登记 + 分层放置 + 同 agent 多会话共用合规 venv + 平台能力优先复用。** 不搞「所有 agent / 所有会话共用一份全局包」，也不搞「每个会话各装一份」。**管理的核心是登记，不是目录默契**。

| 层 | 放哪 | 谁共用 | 登记去处 |
|---|---|---|---|
| 系统运行时（Python / Node / Git） | 系统装一份 | 全机 | `env/toolchain.md` + `memory/devices/tools-<设备名>.md` |
| 平台自带能力（如 `~/.workbuddy/external-packages/` 下的 pdf-cli） | 平台托管，agent **不碰、不重复安装、不自行升级** | 全平台会话 | 平台维护，**无需登记** |
| **通用只读解析库**（pypdf / pdfplumber 等跨任务复用、无项目绑定） | `~/.agent-tools/venvs/<agent名>/` | **同一 agent 名的所有会话共用一份**（不同设备各自一份） | `env/requirements.txt` 固定版本 + `env/toolchain.md` §五 变更日志 |
| 项目专属依赖 / 项目级 CLI | 项目 `node_modules/` + lock 文件 | 随项目 clone 复现 | 项目 `package.json` + lock（四-4 ⑦） |
| MCP 服务 / 定制工具 | 见 四-2 / 四-4 | 同机多 agent 共享同一服务 | `env/mcp-registry.md` |

- **① 平台能力优先复用（安装前第一探测）**：需要解析/转换 PDF、图片、Office 等能力时，先查平台内置 CLI 与本机已有工具（`~/.workbuddy/external-packages/`、`command -v`、`memory/devices/tools-<设备名>.md`）；满足需求即直接调用，**不得安装第三方库**。本次事故的根因正是跳过这一步——平台 pdf-cli 本就能解析，却额外装了 pypdf。
- **② 同 agent 多会话共用一份**：venv 按 **agent 名** 隔离（三-5 ① / 四-1），**不按会话隔离**。同一 agent 名的多个并发会话共用同一个 `venvs/<agent名>/`；开工前先核对 venv 内是否已装且版本符合 `env/requirements.txt`，有则复用，缺则按清单装**一次**并追加变更日志。**禁止每会话各装一份**（重复下载、版本漂移、无法定责）。不同设备视为不同实例，各自维护自己的 venv 与清单（三-1）。
- **③ 跨 agent 不共用**：各 agent 用自己的 venv，禁止激活或改写他人 venv（三-5 ①）。若将来确需跨 agent 共享一批库，须新增 `~/.agent-tools/venvs/_shared/` **只读层**（含版本清单与变更登记），走第十节治理由人类批准后升版实施；**禁止口头破例，禁止改用全局前缀绕过**。
- **④ 禁止以「共享」为由放全局**：`pip install --user`、系统级 `site-packages`、`%APPDATA%\Python\...` 等共享前缀一律违规（三-5 ②）；**不得用「补一条登记」把违规状态合法化**（四-4 ⑦ 存量整改）。理由：① 一个项目锁 5.x、另一个要 6.x 时必然冲突；② 无法从清单追溯谁装的、何时装的；③ 新设备无法复现。
- **⑤ 登记是硬要求**：任何新装 / 升级 / 卸载通用库，必须同时更新 `env/requirements.txt`（写死版本号）并在 `env/toolchain.md` §五 追加一行（日期 | 设备 | 操作 | 库与版本 | 操作者 | 备注），10 分钟内 commit + `git sync`（四-4 ③ / 五-1）。**未登记的安装视为不合规**，与安装位置、会话归属无关。
- **⑥ 存量整改流程**：发现违规副本（用户级 / 系统级 site-packages 等）时按「**确认无会话正在使用** → 卸载违规副本 → 按清单装进合规 venv → 补 `requirements.txt` + 变更日志 + 组织/项目记忆 → commit / sync」处理。若另一会话正在使用该库，须**等其结束或由人类裁决**（三-5 ⑥ 人类操作优先 / 三-5 ⑦ 同 agent 多会话），**禁止直接卸载打断**；历史存量可一并纳入并在登记中注明「存量」。

## 五、 存储与备份策略 (Git + NAS + 百度网盘)

### 1. Git 同步纪律（v1.3 变更：双远端）
- **主库**：Gitee 私有仓库，remote 名 `origin`，是一切同步的**事实基准**。
- **备份库**：GitHub 私有仓库，remote 名 `backup`，**只允许被推送覆盖，禁止在其上直接提交**。
- **推送纪律**：每次推送必须依次执行
  `git push origin --all && git push origin --tags && git push backup --all && git push backup --tags`
  （封装为脚本 `env/git-sync.sh` 或 git alias `git sync`），**禁止只推一个远端**。拉取永远只从 `origin`。
  > 勘误（v1.8.2）：Git 2.55 起 `--all` 与 `--tags` 不可在同一命令混用（报 `fatal: --all and --tags cannot be used together`），必须分步推送。
- **推送前代理核对（v1.8.9；v2.0 起仅 T2 且仅在推送时）**：仅 T2 会话执行，`git sync` 前跑 `bash ~/.agent-shared/env/proxy-check.sh`，确认无全局 `http.proxy` 漂移、代理端口可连、origin/backup 可达且与本地 HEAD 一致；异常时 `[Agent报告]` 提醒人类并停下等确认，**禁止静默改用会话级临时 HTTP 代理绕过**（其端口每会话变化，且不一定能访问 GitHub）。基线：Gitee(origin) 直连，仅 GitHub(backup) 走 `http.https://github.com.proxy`。
- **三重兜底**：夜间备份任务中额外执行 `git bundle create nas-backup.bundle --all`，将 bundle 文件放入 NAS `backup/`，随网盘冷备一起归档——即使两个托管平台同时不可用也可从 bundle 恢复。
- **冲突裁决**：两平台内容不一致时，一律以 Gitee 为准重新覆盖 GitHub。
- **禁止提交内容**：`venvs/`、`node_modules/`、`*.pyc`、`tmp/`、`config/`、任何密钥与大型二进制。
- **依赖更新**：安装新包后，必须立刻更新 `env/requirements.txt` 并与代码改动在同一个 Commit 提交。
- **提交前**：先 `git pull --rebase`，解决冲突并验证通过后再推送。
- **commit message 规范**（v1.8.2）：
  - 格式：`<type>: <简述> by <agent名>@<设备名>`（多账号可加 `~<账号标识>`，见 三-8；仅用于定责，不改 type 枚举），简述用中文、不超过 40 字。
  - `type` 枚举：`docs`（规范/文档）| `feat`（新功能）| `fix`（修复）| `refactor`（重构）| `memory`（记忆）| `handoff`（交接）| `infra`（环境/工具/密钥）| `scripts`（脚本）。
  - 示例：`docs: 规范升级 v1.8.2 — worktree 适用场景+自检标签化+commit 规范`、`fix: git-sync 兼容 Git 2.55 分步推送 by workbuddy@zhn-tbxg2iah-win`。
  - 压缩提交特例：`memory: compact YYYY-MM by <agent名>@<设备名>`。
  - 目的是让 `git log` 可按 type 过滤、按 agent 追溯；历史提交不追溯改写。

### 2. NAS 存储规则
- 挂载点约定：Linux `/mnt/nas`，Windows `Z:\`。
- 超过 20MB、或无需跨设备实时编辑的数据文件、视频、扫描件，必须存放在 NAS 的 `docs/` 对应目录下，**禁止存入 Git 仓库**；需要跨设备实时编辑的重要文档（一般 ≤100MB）走 `~/.agent-docs`（见 二-3）。
- 需要冷备的文件放入 NAS 的 `backup/` 目录，禁止 Agent 在会话中实时读取。
- **跨设备引用规范**：handoff 与记忆中引用 NAS 文件时，统一使用**相对 NAS 根的路径**，格式：`nas://docs/项目名/文件名`。
  > **`nas://` 是文本引用约定，不是操作系统协议**：不安装任何驱动，操作系统本身不识别它。它只存在于记忆/交接文档中，由**各设备自行解析**——解析映射登记在本机 `memory/devices/<设备名>.md`（如 `nas:// → Z:\` 或 `nas:// → /mnt/nas`）。
- **各系统解析方式**：Windows 用内建 SMB 映射 `Z:\`（无需额外软件）；Linux/Termux 挂载 SMB 需安装 `cifs-utils` 后 mount 到 `/mnt/nas`；**无挂载能力的设备（iOS、未 root 的部分 Android）遇到 `nas://` 引用时不得尝试访问**，应提示人类或将该文件改为经 Git 传递副本。
- **NAS 降级行为**：挂载点不可达时，Agent 应立即报告人类并暂停涉及大文件的任务；**禁止**将本应存 NAS 的大文件临时塞进 Git 工作区或 `tmp/` 长期驻留（`tmp/` 停留超过 24h 的大文件视为违规）。

### 3. 百度网盘冷备 (5T 免费空间)
- **定位**：仅用于夜间单向冷备，**严禁 Agent 直连 API 进行高频读写**（受限于限速）。
- **凭证**：使用已申请的官方 API（AppKey/SecretKey），密钥本体存于各设备 `~/.agent-shared/config/`（手动分发，见 六）。
- **脚本**：使用 `rclone` 或定时 Python 脚本，每日凌晨将 NAS 的 `backup/` 推送至网盘。增量备份，不覆盖删除。
- **rclone 后端风险（v1.5 新增）**：百度网盘的 rclone 后端长期属实验性状态，可能因限速/接口变更**静默失败**。因此：
  - **先决验证**：备份方案部署后的第一周，人类每日核对 `manifest` 是否正常生成，确认链路稳定后才转入无人值守；
  - **备选方案**：若 rclone 后端不可用，改为"本地/NAS 上加密打包（7z 加密或 rclone crypt）→ 人工手动上传网盘"，**严禁明文上传**；
- **备份验证（v1.2 新增）**：
  - 每次备份完成后脚本生成 `backup/manifest-YYYY-MM-DD.sha256`（文件清单与校验和），随备份一起上传；
  - 每月人类随机抽取 1–2 个文件走一次**恢复演练**（从网盘拉回并比对校验和）；
  - 备份脚本连续 3 天失败时，必须产生人类可感知的告警，禁止静默失败。**告警渠道具体化**：默认**邮件**（无第三方依赖），可选 Server酱 / Bark 手机推送；渠道与凭证配置在本机 `config/` 并登记进 `keys-checklist.md`。

## 六、 密钥管理（v1.2 新增）

- 密钥**永不入 Git**，采用**手动分发**：新设备初始化时，由人类参照根目录 `keys-checklist.md`（该清单只列密钥名称与用途，不含密钥值）逐项手动复制到本机 `~/.agent-shared/config/`。
- `keys-checklist.md` 与密钥文件必须同步维护：新增密钥时，先更新清单再分发；废弃密钥时，清单标注废弃日期。
- 各设备 agent 在启动自检中核对：清单中的每一项在本机 `config/` 是否存在（只查存在性，不读内容）。缺项时报错并提醒人类补齐。
- **凭据共用边界（v2.2 订正，见 三-8 ⑥⑦；原「多账号主体边界」）**：`config/` 是**设备级**凭证，共用范围限定为**同一台设备 + 同一个 agent 软件**（人类 2026-11-12 11:49／11:50 定义）；该范围内多个平台账号共用一份，不按账号拆分、不单独分发（人类 11:44 裁决，并接受连接器授权机器级共享）。**跨设备、跨 agent 软件禁止**复制／分发同一份私钥／token，禁止搬用登录态与连接器授权；新设备初始化仍按本节由人类手动逐项分发。新增密钥时须在 `keys-checklist.md` 标注「适用设备 + agent 软件」；同一设备同一 agent 软件下若出现不同主体账号，是否仍共用须人类单独裁决。身份／记忆目录 `user-<id>-*` **仍按账号隔离，禁止跨账号复制**，不因本条放宽。

### 1. 防泄漏技术措施 (v1.5 新增)
"密钥不入 Git"不能只靠纪律，仓库根目录**必须**落实：
- **`.gitignore` 强制模板**（存于 `env/.gitignore.template`，clone 后首先复制生效）：
  ```gitignore
  config/
  tmp/
  *venv*/
  node_modules/
  .env
  *.pyc
  ```
- **gitleaks pre-commit hook**：每台设备安装 [gitleaks](https://github.com/gitleaks/gitleaks) 并配置为 pre-commit hook（`gitleaks protect --staged`）。**hook 必须链式委托**：全局 `core.hooksPath` 指向 `~/.agent-tools/hooks`，该 hook 先执行 gitleaks，随后**转发调用项目自身的 pre-commit**（`$(git rev-parse --git-dir)/hooks/pre-commit`），不得整体覆盖 husky 等项目级钩子。Linux/Termux 与 Windows（Git Bash hook 通用）一致。
- **服务端扫描（可选）**：GitHub 私有库的 push protection/secret scanning 属付费高级功能，Gitee 个人版无此功能；**有条件则开启，无条件以本地 hook 为准**。
- **事故处置**：一旦密钥被提交并推送：
  1. **立即轮换该密钥**——仅删除文件无效，密钥已永久留在 Git 历史中；
  2. 在 `keys-checklist.md` 标注泄漏与轮换日期；
  3. 历史清理：简单场景直接**重建仓库**（删库重推，双远端同步重建），保留场景用 `git filter-repo` 清洗后强推双远端；
  4. 排查泄漏窗口期内的 clone 记录（哪些设备/人拉取过）。

## 七、 项目代码（v1.2 新增）

- 本仓库（`~/.agent-shared`）**不同步任何项目代码**。
- 所有项目代码仓库在 `env/repos.md` 登记，每条包含：

  ```
  | 项目名 | Git 地址 | 默认分支 | 本地约定克隆路径 | 简述 | 记忆文件 |
  ```

- agent 需要处理某项目时，按登记表 clone 到约定的本地路径（**统一为 `~/source/<项目名>`**），项目运行时依赖装进 `~/.agent-tools/venvs/<agent名>/`——**venv 按 agent 名隔离、不按项目**（四-5 ②；v1.8.11 删除原文「项目名或agent名」的歧义写法）。
- 项目相关的记忆写在 `memory/projects/<项目名>.md`，并与登记表中"记忆文件"列对应。

### 1. 无代码仓库 / 非 `~/source` 项目（v1.8.11 新增）

> **背景**：现有项目不都是 Git 仓库。`stockdb` 是 NAS 常驻服务，资产在 `/volume1/docker/stockdb/`，无 Git 地址、不在 `~/source/`，此前只靠 `repos.md` 的「无」与项目记忆一句「不适用，勿误判」兜底，新 agent 容易按通用条款误判为「接入未完成」。

- **判定**：`repos.md` 中「Git 地址 = 无」或资产不在 `~/source/<项目名>/` 的项目，即属本类；**必须在「项目属性补充表」登记**，不得省略。
- **明确不适用的条款**：〇② 项目 `AGENTS.md` 挂接（无工作区规则文件）、三-5 ③ 项目目录占用确认（无本地项目目录）、三-6 worktree 协作（无 Git 仓库；`~/.agent-shared` 本就禁用 worktree）、七节 clone 到 `~/source` 的约定。**agent 不得据此判定「接入未完成」，也不得为它创建 `~/source/<项目名>/` 占位目录**。
- **仍然适用的条款**：三-1 项目记忆独立文件、三-4 交接与 `项目:` 标签、三-5 ⑤ 任务认领、三-7 部署权限（引擎启停 / 容器重启 / 升级一律属部署）、六 密钥、八 启动自检、四-5 通用库分层。诊断类工作默认只读。
- **项目属性补充表**（`env/repos.md` 第二节，必填字段）：`项目名 | 资产位置 | AGENTS 挂接 | 部署入口 | 凭据落点 | 不适用条款声明`。所有项目都登记，不只本类项目。
- **项目级凭据落点**：wrangler OAuth、云厂商 token、NAS SSH 等落在**项目本地或平台凭据库**的，不进 `config/`、也不列入 `keys-checklist.md` 的 `config/` 存在性核对（避免自检第 1 步误报缺项）；但**必须在补充表「凭据落点」栏写明位置与是否入 Git**。凭据文件一律不得提交（六-1 gitleaks 兜底），项目根下的登录输出类文件须加入项目 `.gitignore`。

## 八、 Agent 启动自检指令 (必读)

当你（Agent）启动或接入新任务时，请按顺序执行以下自检。标签含义：`[Agent自动]` = agent 自行判定并完成；`[Agent报告]` = agent 只能检查并上报状态，处置权在人类；`[人类执行]` = agent 无法完成，必须请人类操作。

> **档位门槛（v2.0，见 〇⑦，先于以下步骤执行）**：先判定 T0 / T1 / T2 并在第一个输出声明。**下列 1~10 步仅 T2 会话全量执行**；T0 纯对话／只读不执行、T1 本机单会话不执行，两者只遵守 〇⑦ ③ 最小红线集。人类显式要求「开工前按规范自检」时强制 T2（〇④）。一旦会话中途转为写共享仓／安装／部署／认领任务卡／`git sync`，立即升为 T2 并补做自检；**升降档只影响加载量，不改变共享仓写入纪律**。

1. **[Agent自动]** 检查 `~/.agent-shared/memory/` 记忆目录是否正常；核对 `keys-checklist.md` 中各项在本机 `config/` 是否存在（缺项即提醒人类；多账号时按 三-8 只核对当前账号适用的凭证项）；**检查 `config/` 目录权限**——Linux/Termux 应为 `700`/文件 `600`，Windows 确认未共享给其他用户，权限过宽即提醒人类收紧（缺项与权限整改属 `[人类执行]`）。
2. **[Agent报告]** 检查本地 MCP 服务是否在线（尝试访问 `127.0.0.1:9101`）。如果不在线，提醒用户运行 `~/.agent-shared/env/start-mcp.sh`（Windows 为 `start-mcp.bat` 或对应计划任务）——启动服务涉及人类环境决策，MCP 未起时不得阻塞其他自检项。
3. **[Agent自动]** `git pull --rebase` 同步最新状态；读取 `~/.agent-shared/handoff/` 下最新的交接文档，同步当前上下文（按 三-1 加载策略，默认只读最新一份、org.md 只读最近 200 行），并核对其中的「挂起任务」快照（三-4）；**本会话涉及多个项目时，按项目各补读最近一份带 `项目:` 标签的 handoff**（v1.8.11）。远端未配置或网络不可达时降级为 `[Agent报告]`，如实上报并继续。
4. **[Agent自动]** 检查 `memory/.compact-lock` 是否存在：存在则本会话**暂停写入记忆**（其他设备正在压缩），可正常读。
5. **[Agent自动]** 确认当前是否激活了位于 `~/.agent-tools/venvs/` 下的专属虚拟环境（查 `$VIRTUAL_ENV`）。
6. **[Agent自动]** 若本会话需要手动安装的定制 MCP，先查 `env/mcp-registry.md` 确认本机是否已安装及版本是否一致。
7. **[Agent报告]** 若本会话涉及重要文档，确认 `~/.agent-docs` 同步目录可达且同步状态正常（长期未同步/冲突文件堆积时，先提醒人类处理，禁止在未同步状态下直接编辑覆盖；同步冲突的处置一律由人类在客户端完成，见 三-5 ⑥）。
8. **[Agent自动] 工具链核对（v1.8.3）**：检查 `~/.agent-tools/run/tools-scan.stamp` 是否存在——
   - **不存在（本机首次运行）**：执行 `bash ~/.agent-shared/env/tools-scan.sh --write`，生成 `memory/devices/tools-<设备名>.md`，并在 `env/toolchain.md` §六 登记本设备，提交后 `git sync`；
   - **存在且未满 30 天**：**不再全量扫描**，只跑 `bash ~/.agent-shared/env/tools-scan.sh --check`，基线通过即继续；缺项或低于基线时上报人类；
   - **存在但超 30 天**：重新 `--write` 刷新一次，结果入库存档。
   禁止跳过本步直接安装工具（先探测，再决定是否安装，见 四-4 ①）；需要解析/转换类能力时先探测平台内置 CLI 与合规 venv 内已登记的通用库，禁止直接下载第三方库（见 四-5 ①②）。
9. **[Agent自动] 规范注入确认（v1.8.5，见 〇）**：确认本会话上下文已包含本规范全文或全局指令指针；没有则立即读 `~/.agent-shared/global/rules.md`。若任务涉及 `~/source/` 下项目，检查其 `AGENTS.md`/`CODEBUDDY.md` 首部是否已挂接全局规范（〇 ②），未挂接则登记到 `memory/projects/<项目名>.md` 并提醒人类，不擅自改写。
10. **[Agent自动] 代理与双远端核对（v1.8.9，见 五-1）**：执行 `bash ~/.agent-shared/env/proxy-check.sh`，确认无全局 `http.proxy` 漂移、代理端口可连、origin/backup 可达且与本地 HEAD 一致；异常时按 `[Agent报告]` 提醒人类并停下等确认，禁止改用会话级临时代理绕过。每次 `git sync` 推送前必须重跑一次。

## 九、 人类用户的初始化清单 (供参考)

1. 在 Gitee 建私有仓库 `agent-workspace`（主库），在 GitHub 建私有备份仓库，本地 clone 后添加双远端并配置 `git-sync` 推送脚本（见 五-1）。
2. 在系统层面装好 Python、Node.js、Git、rclone（Windows 上另装 Git Bash，随 Git for Windows 自带）。
3. 创建 `~/.agent-tools` 目录，初始化 `venvs`、`mcp`、`bin`、`run` 等子目录。
4. 在 `env/` 下编写一键安装依赖的 `setup.sh`（Linux/Termux）与对应 Windows 脚本，及 `start-mcp.sh` 与 Windows 版 `start-mcp.bat`；将 `env/.gitignore.template` 复制为仓库根目录 `.gitignore`；每台设备安装 gitleaks 并配置 pre-commit hook（见 六-1）。
5. 按 二-0.5 命名本设备并登记进 `memory/devices/_devices.md`，同时在本机 `memory/devices/<设备名>.md` 写入本机挂载映射与端口信息。
6. 建立 Windows 侧的 PowerShell 计划任务：MCP 开机自启、`tmp/` 7 天清理、夜间百度网盘备份（含 `git bundle`）。
7. 选定统一的文档同步工具（建议坚果云），安装并配置全部接入设备，将本地同步目录指向 `~/.agent-docs`（或建符号链接），凭证按 六 手动分发。
8. 参照 `keys-checklist.md` 将密钥手动复制到新设备 `config/`，并逐项核对。
9. 在 `env/mcp-config.json` 配置公开市场 MCP；手动安装的定制 MCP 逐条登记进 `env/mcp-registry.md`。
10. 在 `env/repos.md` 登记所有项目代码仓库地址，并为每个项目填写「项目属性补充表」（见 七-1）。
11. **指定主设备**（负责月度记忆压缩）并写入设备登记表。
12. 将本文件（`global/rules.md`）发送给所有接入的 Agent 阅读。

## 十、 治理（v1.2 新增）

- **裁决人**：本规范的唯一维护者与冲突最终裁决人是仓库所有者（人类用户）。任何 agent 无法解决的冲突、规范未覆盖的场景，一律上报人类裁决，不得自行创设规则。
- **副裁决人 (v1.5 新增)**：人类可指定一名副裁决人（写入本节及 `memory/devices/_devices.md` 备注），在所有者不可用时（离线、授权范围外）代理规范级冲突的临时裁决；副裁决人的裁决需在所有者下次在场时追认。未指定副裁决人时，冲突一律挂起等待所有者。
- **修订流程**：规范变更由人类批准后修改 `global/rules.md`，并在顶部"变更记录"追加条目；所有设备在下一次自检时通过 `git pull` 自然获取新版。
